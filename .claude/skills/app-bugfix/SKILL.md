# app-bugfix — 재현 → 원인 → 실패 먼저 → 수정 → 같은 화면 확인

버그 수정의 증거는 "같은 화면에서 전에는 틀렸고 지금은 맞다"이다. 단위 테스트 통과는 분기 동작을 보여 줄 뿐 버그가 사라졌다는 증거가 아니다. 앱 조작은 app-verify 스킬을 쓴다.

## 1. 실제 앱에서 재현한다

- app-verify 로 빌드·실행하고, 제보된 화면까지 Maestro 흐름으로 간다. 사람에게 재현을 부탁하지 않는다. 쓰기 동작(로그인·투표·글쓰기 등) 뒤에만 나타나는 버그처럼 자동 흐름이 갈 수 없을 때만, 어디까지 갔는지와 막힌 이유를 적어 사람에게 넘긴다.
- 재현되면 그 흐름을 `flows/bug-<짧은이름>.yaml` 로 남긴다. 버그가 있는 동안 이 흐름이 **실패**해야 한다(틀린 화면에서 기대한 글자가 안 보이는 식). 실패 스크린샷이 재현 증거다.
- 재현이 안 되면 조건을 좁히거나(같은 ETF·같은 탭·느린 네트워크), 로그(`logcat.txt`)를 늘려 다시 한다. 재현 없이 고치지 않는다.

## 2. 원인을 좁힌다

- 후보 원인을 적고, 남은 범위를 가장 크게 줄이는 확인부터 한다(API 응답이 틀렸나 → 앱이 잘못 그리나 → 상태가 꼬였나).
- API 가 의심되면 같은 요청을 `curl https://etforca.edgesignal.dev/api/v1/...` 로 직접 본다(읽기 요청만).
- 추측으로 고치지 않는다. 원인이 런타임 증거로 하나 남을 때까지 줄인다. "도움이 될 수도 있는" 보조 수정은 넣지 않는다.

## 3. 실패를 먼저 커밋한다

- 값싼 테스트 경로가 있으면(`apps/etforca/app-ui/tests/*.test.cjs` 처럼 순수 함수) 실패하는 테스트를 먼저 쓰고 커밋한다(mattpocock tdd 스킬).
- 없으면 1의 `flows/bug-*.yaml` 를 먼저 커밋한다. git 기록에서 실패 확인이 수정보다 앞에 온다.

## 4. 고친다

- 증거가 정당화하는 가장 작은 변경만. 인터페이스·저장 형식·API 계약이 바뀌면 고치기 전에 설계를 적고 확인받는다.
- 네이티브 모듈·의존성·app.config 를 바꾸면 Android 빌드 CI(`app-android-build`)가 필수다.

## 5. 같은 화면에서 다시 확인한다

- 새 APK 를 빌드해 `launch.sh` 로 설치하고 `run.sh` 를 돌린다. 재현 흐름이 통과하고, 나머지 흐름도 전부 통과해야 한다.
- 화면 모양이 바뀌는 수정이면 app-design 의 `shotdiff.py` 로 고치려던 화면 외에 바뀐 화면이 없는지 본다.
- "확인 불가"나 다른 화면에서의 확인은 통과가 아니다. 그렇게 적는다.

## 6. PR

pr-cycle 을 따른다(edge-review 수렴 → docs-sync → dev 대상 PR → Codex 리뷰). PR 본문에 붙일 것:
- 재현 증거: 수정 전 실패 스크린샷, 흐름 이름
- 원인 한 줄
- 수정 후 증거: 같은 흐름 통과 스크린샷, `report.xml` 요약, `app-errors.txt` 줄 수, 증거 폴더의 커밋

사람은 코드보다 전/후 스크린샷을 먼저 본다.

## 지적 → 검사

리뷰나 사람이 같은 종류의 실수를 두 번 지적하면, 규칙 문서 대신 다음 중 가장 높은 단계로 막는다:
1. 구조로 없앤다(상태 주인 하나, 지원하는 방법 하나, 옛 방법 삭제).
2. 타입으로 못 쓰게 한다.
3. 린트·CI 검사로 막고, 오류 메시지에 대신 쓸 것을 적는다.
4. 테스트·Maestro 흐름으로 동작을 확인한다.
5. 그래도 판단이 필요한 것만 문서에 적는다.

새 검사는 실제로 있었던 실수에서 실패하는지 확인한다. 예: `app-android-build` 는 #1605 시점 코드에서 실패하는 것을 확인했다(#1656). 만든 검사는 app-verify 의 "규칙과 그 규칙을 지키게 하는 장치" 표에 더한다.
