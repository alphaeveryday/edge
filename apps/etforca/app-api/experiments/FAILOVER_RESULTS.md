## write-behind vs db-first — S2 master SIGKILL, 재투표 부하 (2026-09-19)

같은 하네스·같은 부하(k6 50rps×180초, `USER_POOL=3000` — 사용자 3,000명이 라운드마다 다른 선택으로 재투표, 60초 후 master SIGKILL)로 두 쓰기 정책을 나란히 실측했다. 런: write-behind `S2-20260919-172433`, db-first `S2-20260919-172955`. 판정은 선택지별 합계·`HLEN`·중복행에 더해 **사용자별 최종 choice 를 k6 ack·DB·Redis 세 방향으로 대조**했다(`per-user.json`).

| 지표 | write-behind | db-first |
|---|---|---|
| 응답 코드 | 200 8,362 / **503 639** | 200 9,000 |
| 투표 거부 구간 | 12.8초 (서킷 open 포함) | 0 |
| failover (+switch-master − fault) | 5.9초 | 6.8초 |
| 투표 p99 / max | 5.1ms / 84.9ms | 7.2ms / 113.7ms |
| 무관 요청 p99 | 3.4ms | 2.6ms |
| Tomcat busy 최대 | 3 | 3 |
| Redis 쓰기 실패(폴백) | 639 → 전부 503 | 638 → 전부 200, DB 커밋 |
| ack 받은 표의 유실 (`ack_db_mismatch`) | **0** | 0 |
| 최종 DB=Redis (사용자별) | 3,000 / 3,000 | 3,000 / 3,000 |
| 복구 수단 | warm(재연결 시 적재 0건 — 승격 레플리카에 전부 있었음) | 재조정(재연결 트리거, choices 통째 교체) |

해석:

- **같은 장애 창(약 13초)에서 두 정책은 같은 639±1건을 서로 다르게 처리했다.** db-first 는 DB 에 커밋하고 200 을 돌려준 뒤 재조정으로 Redis 를 맞췄고, write-behind 는 DB 우회가 없으므로 503 으로 반려했다. 유실은 양쪽 다 0 — write-behind 의 0 은 "받은 표는 안 잃었다" 이지 "표를 안 잃었다" 가 아니다. 639건은 클라이언트가 재시도해야 한다.
- **write-behind 의 미flush 유실은 이 런에서 관측되지 않았다.** master 가 죽는 순간 레플리카에 복제 안 된 표가 있어야 유실인데, 로컬 단일 호스트의 복제 지연은 3초 flush 주기보다 훨씬 짧아 승격 레플리카가 전부 갖고 있었다(warm 적재 0). 유실 상한은 복제 지연 × 쓰기율이며 네트워크 분단(S4)·완전 장애(실험 5)에서 따로 봐야 한다.
- **재투표 부하에서 선택지별 합계 delta 는 오류를 숨긴다.** db-first 런의 재조정 로그는 delta 가 ±1 뿐인데, 장애 구간 638건의 재투표는 회전 패턴(BUY→HOLD→SELL→BUY)이라 합계가 상쇄됐다. 실제로는 choices 해시 638건이 낡아 있었고 재조정의 통째 교체가 고쳤다. 사용자당 1표 부하로 쌓은 이전 기록의 "실패 로그 ≈ 재조정 delta" 검산은 재투표 부하에서 성립하지 않으며, 사용자별 3방향 대조가 그 자리를 대신한다.
- 지연·스레드 지표는 두 정책이 같은 급이다. write-behind 가 p99 에서 약간 낮은 것은 커밋 경로가 없어서이지만 이 부하(50rps)에서는 차이가 의미 있는 크기가 아니다. 쓰기 한계 TPS 비교(실험 1·2)는 별도 스파이크 부하가 필요하다.

## write-behind vs db-first — S4 네트워크 분단, 재투표 부하 (2026-09-19)

S2 와 같은 부하(`USER_POOL=3000`)로, 60초 후 원래 master 컨테이너만 compose 네트워크에서 분리했다(`docker network disconnect`). 런: write-behind `S4-20260919-173616`, db-first `S4-20260919-174124`.

| 지표 | write-behind | db-first |
|---|---|---|
| 응답 코드 | 200 8,277 / **503 723** | 200 9,001 |
| 투표 거부 구간 | 13.9초 | 0 |
| failover (+switch-master − fault) | 7.1초 | 7.1초 |
| 투표 p99 / max | 8.0ms / 519ms | **116.8ms / 822ms** |
| 100ms 초과 / 400ms 초과 | 65 / 55 | 95 / — |
| 무관 요청 p99 | 3.5ms | 2.4ms |
| Tomcat busy 최대 | 11 | **22** |
| Redis 쓰기 실패(폴백) | 723 → 503 | 727 → 200, DB 커밋 |
| ack 받은 표의 유실 | 0 | 0 |
| 최종 DB=Redis (사용자별) | 3,000 / 3,000 | 3,000 / 3,000 |
| 분리된 구 master 상태 | `role:master`, `connected_slaves:0` 유지 | 동일 |

해석:

- **분단은 kill 과 실패 형태가 다르다.** SIGKILL 은 연결이 즉시 끊겨 REJECT_COMMANDS 가 바로 실패시키지만, 분단은 연결이 살아 있는 채 응답만 안 와서 **커맨드 타임아웃 500ms 를 끝까지 기다린다**. 서킷이 열리기 전 최소 호출 수(10)만큼은 두 모드 다 500ms 꼬리를 먹었다(write-behind max 519ms·400ms 초과 55건). 서킷이 열린 뒤에는 즉시 폴백이라 꼬리가 사라진다 — S2 실측이 못 보여 준 서킷의 존재 이유가 여기서 드러난다.
- **db-first 는 그 500ms 동안 Tomcat 스레드와 DB 커넥션을 같이 잡는다.** AFTER_COMMIT 리스너가 커밋 후·커넥션 반환 전에 Redis 를 호출하므로 대기가 트랜잭션 꼬리에 얹힌다(busy 최대 22, max 822ms, p99 117ms). write-behind 는 DB 를 안 잡으니 Redis 대기만 남는다(busy 11, p99 8ms). 이 부하(50rps)에선 둘 다 SLO 1초 안이지만, 스레드 점유 차이는 부하가 오르면 db-first 쪽이 먼저 포화한다는 뜻이다(S1 5초 타임아웃 실측의 200/200 포화와 같은 축).
- **유실은 양쪽 0.** 구 master 는 분단 후에도 자신을 master 로 알았지만(`connected_slaves:0`), 이 하네스는 앱도 구 master 에 못 닿게 만들므로 분단 후 거기에 쓰인 표가 없다. 앱과 구 master 가 같은 쪽에 남는 분단(진짜 split-brain)은 이 하네스로는 못 만들며, 그 경우 write-behind 는 구 master 에 쓰인 표를 재합류 시 통째로 잃는다 — `min-replicas-to-write` 가 그 방어이고 실험 4 의 후반(유무 비교)은 미실행이다.
- 재투표 부하에서 합계 delta 가 상쇄되는 현상은 S2 와 같다(db-first 재조정 로그 3줄, 사용자별 대조로만 확인).
