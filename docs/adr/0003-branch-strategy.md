# ADR-0003: 브랜치 전략 — dev 경유 엄격한 사다리

- 상태: 승인됨
- 날짜: 2026-06-21

## 맥락
`main`은 항상 배포 가능해야 하고, 변경을 모아 검증할 통합 지점이 필요하다.
직접 push로 `main`이 불안정해지는 것을 막아야 한다.

## 결정
네 종류의 브랜치를 둔다 — `main`(릴리스 기준, 항상 배포 가능) / `dev`(통합) / `feature/*` / `fix/*`.
**엄격한 사다리**로 PR 경로를 고정한다:
- `feature/*`·`fix/*` → **`dev`에만** PR.
- `dev` → **`main`에만** PR.
- 따라서 `main`은 **오직 `dev`에서 온 PR만** 받는다. 핫픽스도 예외 없이 `fix/* → dev → main`.
- 릴리스는 `dev → main` 머지 후 `main`에 태그.

운영 규칙 본문은 [README.md](../../README.md)의 "Git 컨벤션"이 SSOT.

## 대안
- **GitHub Flow(main + feature만)** — 통합 검증 지점이 없고, 다수 변경이 곧장 main으로 향해 위험하다.
- **핫픽스의 main 직결 경로 허용** — main 브랜치 보호에 예외 경로와 dev 백머지 규칙이 추가로 필요해 복잡해진다. 단순함을 위해 폐기(모든 변경 dev 경유).

## 결과
- `main`은 항상 배포 가능한 상태로 유지된다.
- 브랜치 보호 규칙이 단순하다 — `main`의 허용 소스가 `dev` 하나뿐.
- 긴급 핫픽스도 `dev`를 한 단계 거치므로 약간 느리다(수용한 트레이드오프).
- 머지 방식은 [[0007-merge-strategy]]를 따른다.
