# ADR-0064: 뉴스 태깅을 로컬 RoBERTa로 바꾸고, 스레드 단계는 시간 공백 규칙으로 나눈다

- 상태: 제안됨 (코드 ALPHA-1446 · 스레드 규칙 ALPHA-508 · 스레드 창 ALPHA-1474 · 운영 전환은 인프라 PR에서 `TAGGER_BACKEND=roberta`)
- 날짜: 2026-10-24

## 맥락
- 뉴스 태깅 세 경로(1분 `news-consumer`, 배치 `tag-news`, 배치 `assemble-events`)가 기사마다 DeepSeek을 부른다. 외부 API의 비용과 장애가 태깅 커버리지를 정한다.
- 스레드 규칙(`thread_events`)은 같은 사건의 후속 단계와 재보도를 가르지 못한다. identity 역할이 같으면 시간 제한 없이 한 스레드로 묶여, 첫 기사 뒤는 모두 재보도가 된다.
- 연구에서 정답셋을 새로 만들고 로컬 모델과 스레드 규칙을 측정했다. 연구 기록은 저장소 밖(`research_notes/news-tagging-jevk5`)에 있고, 이 문서는 결론만 옮긴다.
  - 파싱 정답: 약 1.6만 건(학습 1.5만, 평가 전용 아웃 샘플 3,349건)
  - 스레드 정답 v2: 1,231건, 31개 회사 구간, 후속 단계 47건

## 결정
1. **태깅은 로컬 RoBERTa로 한다.** `klue/roberta-large` 분류기(문서 분류 + 사건 타입 53)와 QA 인자 추출기 두 개를 int8로 바꿔 CPU에서 돌린다. 세 경로 모두 같은 태거를 쓴다(`tagging/roberta.py`, `tagging/backend.py`).
2. **전환은 설정 하나로 한다.** `TAGGER_BACKEND=roberta|llm`이고 코드 기본값은 `llm`이다. 모델 묶음을 올리고 태스크 크기를 키우기 전에 이 코드가 배포돼도 동작이 바뀌지 않는다. 되돌릴 때도 같은 설정을 쓴다. DeepSeek 코드는 1~2주 안정 운영 뒤 별도 PR로 지운다.
3. **모델 묶음은 레이크 `models/tagger/<버전>/`에 둔다.** int8 state_dict를 `weights_only`로 읽는다(피클 실행 없음). 묶음 버전이 코드의 `ROBERTA_TAGGER_VERSION`과 다르면 기동을 거부한다. 묶음은 `scripts/export_tagger.py`로 만든다.
4. **뉴스 스레드는 T5 규칙으로 하고, 창은 7일로 한다(ALPHA-508, 창 재측정 ALPHA-1474).**
   - 키는 같은 회사·같은 타입이다. 증권사 리포트 타입은 증권사까지 같아야 한다. identity 역할 키는 공시에만 남는다.
   - 같은 키의 마지막 보도에서 7일 넘게 끊기면 새 스레드다. 처음에는 6개월(183일)로 정했지만, 45일보다 긴 구간 정답으로 다시 재서 7일로 줄였다(아래 "스레드 창 재측정").
   - 스레드 안에서 하루 넘게 보도가 끊겼다가 다시 나오면 후속 단계(`FOLLOW_UP_STAGE`)다.
   - 모델 호출이 없는 결정적 규칙이다. 회사가 없을 때만 UNKNOWN이다.

## 근거 (측정)
**태깅** — 아웃 샘플 3,349건, 같은 채점기(규칙만)

| | 타입 정확도 | 인자 완화 F1 |
|---|---|---|
| 연구 fp32 | 0.914 | 0.766 |
| 연구 int8 | 0.914 | 0.768 |
| 운영 모듈 int8 (`RobertaTagger`) | 0.916 | 0.765 |

- 운영 모듈과 연구 int8의 쌍대 95% 신뢰구간: 타입 −0.1 ~ +0.4%p, 인자 −0.8 ~ 0.0%p.
- 인자 차이는 동적 양자화가 한 묶음의 값 범위를 쓰는 데서 온다. 연구 측정은 질의를 한 묶음 더 넣었다.

**스레드** — 정답 v2, 평가용 16배치. 설정은 다른 15배치에서 골랐다.

| 방법 | 스레드 B³ | 첫 기사·후속·재보도 매크로 F1 | 후속 단계 F1 |
|---|---|---|---|
| 지금 규칙 계열(T1, 3일 창) | 0.877 | 0.603 | 0.00 |
| **T5** (7일 창 + 하루 공백) | 0.889 | 0.715 (+0.04 ~ +0.18) | 0.34 |
| T6 (JevK5 쌍 판정 30일 + 하루 공백) | 0.894 | 0.782 (+0.12 ~ +0.24) | 0.52 |

- 스레드 묶기는 세 방법의 차이가 유의하지 않다. 구분 성능은 유의하게 좋아졌다.

**스레드 창** — T5, 하루 공백 규칙은 같고 창만 바꿈. 같은 평가용 16배치, RoBERTa 파싱.

| 창 | 스레드 B³ | 정답 스레드 정확 재현 | 매크로 F1 | 후속 단계 F1 |
|---|---|---|---|---|
| 7일 | 0.889 | 0.784 | 0.715 | 0.342 |
| 30일 | 0.857 | 0.617 | 0.743 | 0.448 |
| 6개월 (처음 결정값, ALPHA-1474에서 7일로 변경) | 0.853 | 0.593 | 0.736 | 0.435 |

- 창이 길면 몇 주 떨어진 후속 단계(증설 발표 → 착공)를 같은 스레드로 잡는다. 대신 같은 회사의 다른 사건(다른 계약, 다른 분기 실적)이 합쳐진다.
- 6개월은 실제보다 좋게 나온 값이다. 정답의 회사 구간이 최대 45일이라 45일보다 긴 창의 과연결은 재지 못했다. 운영에서는 한 스레드에 섞이는 사건이 이 표보다 많을 수 있다.

**스레드 창 재측정 (ALPHA-1474, 2026-10-30)** — 회사·사건 유형별 최대 6개월 구간 75개(계약·실적·인수·인증·법률, 1,515건). 운영 DB에 저장된 인자로 T5를 돌렸다. 정답은 두 에이전트(Claude, Codex)가 따로 단 라벨이다(서로 일치도 스레드 B³ 0.947). 사람 정답이 아니고, 병합 전 사람 검수 표본으로 확인한다.

| 창 | 스레드 B³ (Claude / Codex 라벨) | 7일 대비 차이 95% 구간(회사 묶음 부트스트랩) |
|---|---|---|
| 3일 | 0.835 / 0.832 | +0.011 ~ +0.025 / +0.012 ~ +0.034 |
| **7일** | **0.818 / 0.809** | — |
| 14일 | 0.804 / 0.787 | −0.022 ~ −0.007 / −0.033 ~ −0.013 |
| 30일 | 0.775 / 0.748 | −0.060 ~ −0.025 / −0.087 ~ −0.039 |
| 183일 | 0.654 / 0.620 | −0.207 ~ −0.111 / −0.225 ~ −0.149 |

- 창이 길수록 같은 회사의 다른 사건이 한 스레드로 합쳐진다. 이 표는 수집된 기사 전부(사건이 아닌 기사 포함)를 묶은 값이라, 짧은 창이 유리하게 나온다. 라벨러가 고른 관련 기사만 쓰면 3~30일은 7일과 차이가 없고, 183일은 낮다(Codex 라벨에서만 유의).
- 창은 세 측정을 함께 보고 정했다.
  - 긴 쪽 한계: 위 표에서 30일부터 크게 낮아지고, 183일은 두 라벨 모두 크게 낮다. v2 정답(RoBERTa 파싱)에서도 30일·183일이 7일보다 유의하게 낮다.
  - 짧은 쪽 한계: 3일은 후속 단계를 못 잡는다(관련 기사 기준 후속 F1이 7일 0.13 / 0.22, 3일 0 / 0.16). v2 정답(정답 파싱)에서는 3일·5일 모두 7일보다 스레드 B³가 낮고, 3일은 후속 F1도 낮다.
- 7일과 10일은 v2 정답에서 스레드 B³가 구분되지 않는다(10일은 RoBERTa 파싱 후속 F1이 조금 높다). 7일이 최적이라는 근거는 아니다.
- 끊긴 뒤 다시 나온 관련 기사가 앞 사건과 같은 스레드인 비율(라벨러 판정, Claude / Codex): 3~7일 10/15 / 11/17, 7~30일 12/18 / 7/21, 30일 넘게는 6/35 / 7/37.
- 연구 기록: 저장소 밖 `RESEARCH/THREADING_V02/REPORT_V03.md`·`newset/posthoc/window_sweep/`.

**자원** — 이미지와 같은 torch 2.11.0+cpu에서 잼, i9 1코어 기준

| 항목 | 값 |
|---|---|
| 모델 묶음 | 836MB |
| 기동 피크 메모리 | 1.83GB |
| 기사당 시간 | 1.55초 |
| 이미지 증가 | 약 1.1GB |

- Fargate 실측은 아직 없다.

## 대안
- **DeepSeek 유지**: 정확도는 비슷한데 비용과 외부 장애가 남는다.
- **T6(JevK5 쌍 판정)**: 후속 단계 F1이 더 높다(0.52 대 0.34). 하지만 GPU 서버가 필요하다. 지금 JevK5는 AWS 밖 홈서버에 있고 중계(Pinggy)로만 닿아서 운영 경로에 넣을 수 없다.
- **JevK5에게 "같은 단계인가"를 직접 묻기(T4)**: 후속 단계 F1이 0.27로 시간 공백 규칙보다 낮았다.
- **fp32 모델**: 정확도는 같고, 1.7배 느리고, 메모리가 3.2GB다.
- **fp32 파일을 읽고 실행 중에 int8로 변환**: 순간 메모리가 4.9GB까지 올라 태스크에 안 들어간다. 그래서 미리 변환한 int8 묶음을 쓴다.

## 결과
- DeepSeek 호출이 0이 된다. 대신 태깅 태스크가 1 vCPU·3GB로 커진다. 지금 1분 컨슈머는 0.5 vCPU·1GB다.
- 모델을 다시 학습하면 묶음과 `ROBERTA_TAGGER_VERSION`을 같이 올린다. `tag-news`는 버전이 바뀐 기사를 다시 태깅한다.
- 뉴스 스레드 키가 바뀌는 시점에 계보가 한 번 끊긴다. 이전 identity 키로 묶인 뉴스 스레드는 그대로 남지만, 새 보도는 이어받지 않고 새 키로 시작한다. 두 키의 의미가 달라 옮길 대응이 없다. 공시 스레드는 영향이 없다.
- 창을 183일에서 7일로 줄여도(ALPHA-1474) 이미 만든 스레드와 링크는 다시 계산하지 않는다. 마지막 보도가 7일보다 오래된 스레드에 새 보도가 오면 새 스레드가 열린다.
- 창이 짧아져, 늦게 온 과거 보도가 이미 갈라진 두 구간 사이를 이어도 합치지 않는 천장(`thread_events` docstring)이 자주 생긴다. 백필 순서(과거→현재)로는 피할 수 있지만, UNKNOWN 재평가(회사가 나중에 해소된 보도)는 순서가 뒤섞여 피하지 못한다.
- **남은 후속 보도 판정 작업**(이 결정이 닫지 않은 것):
  1. **후속 단계 F1이 0.34다(7일 창, 6개월 창이면 0.44).** 시간 공백만 본다. 7일을 넘겨 다시 나온 같은 사건의 후속은 새 스레드의 첫 보도가 된다.
     - 같은 날 이어진 단계(예: 수요예측 결과 → 공모가 확정)를 놓친다.
     - 하루 넘게 쉬었다 다시 나온 재보도를 후속 단계로 잘못 본다.
     - 다음 후보는 타입 가족별 단계 단서(MOU→본계약, 예비심사→증권신고서)와, 모델이 단계(stage)를 직접 내게 하는 학습이다. 정답에 stage 라벨이 있다.
  2. **회사 연결 오류**: 시세 기사(예: "상장 첫날 ○% 급등")를 사건 기사로 분류해 엉뚱한 스레드에 붙인다. 정답 파싱이면 스레드 B³가 0.937인데 RoBERTa 파싱이면 0.894다. 이 차이 대부분이 여기서 나온다. 시세 기사 학습 데이터를 보강해야 한다.
  3. **같은 원문 판정(3-gram)이 약하다.** v2 정답에서 쌍 F1이 0.54다.
     - 원인은 같은 틀의 다른 리포트("[리포트 브리핑] 회사, '…' 목표가 N원 - 증권사")다.
     - 숫자·인용구 필터를 붙이면 0.67이다. 다만 라벨러 일치도가 0.686이라, 같은 원문의 정의부터 다시 정해야 한다.
  4. **스레드 정답이 작고 짧다.** 평가용 16배치에 후속 단계가 22건뿐이라 신뢰구간이 넓다. 6개월 구간 재측정(ALPHA-1474)도 에이전트 라벨이고 후속 단계가 21~23건뿐이다.
  5. **지침 충돌**: 스레드 지침 v2의 IPO 단계표는 "상장 첫날"을 단계로 두는데, 파싱 지침 R33은 상장 첫날 시세 기사를 시세 기사로 본다.
  6. **Fargate 속도 실측**: i9의 절반 속도로 가정했다. 9시 피크를 1태스크가 감당하는지는 전환 첫날 지연으로 확인한다.
  7. **사건 타입 범위 밖의 거시 지표**: 최근 기사에서 EVENT로 분류된 기사의 52%가 사건 타입 없이 버려진다.
     - 정답셋(OOS 3,349건)으로 보면 대부분 맞는 판정이다. "사건이지만 타입 없음" 예측 841건 중 721건(86%)은 정답도 카탈로그 밖 사건이다. 타입이 있는 사건을 이 판정으로 놓친 것은 56건(3.3%)이다.
     - 그래서 2순위 타입으로 채우는 수정은 하지 않는다. 56건을 살리는 대신 721건에 틀린 타입이 붙는다.
     - 버려지는 기사 대부분은 상장 종목과 무관하다(지자체 협약, 지역 소식, 국감 발언, 분양). 다만 일부는 카탈로그에 타입이 없는 거시 지표 발표다. 수출입 통계, 통화량·가계대출, 주택 가격·거래가 그렇다.
     - 이 지표를 MACRO 타입으로 넣을지는 ETF 분석에 쓸 가치로 정한다. 넣으려면 정답 라벨 추가, 분류기 재학습, 묶음 배포가 함께 필요하다.
