# 가격 변동 설명 비교 벤치마크 설계

같은 당시 자료를 받은 우리 시스템과 Gemini의 답변을 공정하게 비교한다.
그럴듯하지만 근거가 없거나 시점이 맞지 않는 설명은 좋은 점수로 상쇄하지 않는다.
웹을 자유롭게 쓰는 Gemini 결과는 참고용으로만 따로 보며, 투자 판단의 근거로 쓰지 않는다.

## 용어집

| 용어 | 뜻 | 코드·원어 |
|---|---|---|
| 시점 고정 | 해당 기준 시각에 알 수 있었던 자료만 쓰는 규칙 | point-in-time, PIT |
| 증거 묶음 | 사례별로 고정한 수치·원문·시각·출처의 불변 입력 | evidence packet |
| 우리 시스템 | 증거 묶음만 검색해 설명을 만드는 비교 대상 | O-PIT |
| Gemini 동일입력군 | 사람이 Gemini에 같은 증거 묶음을 주는 비교 대상 | G-PIT-RAG |
| Gemini 자유웹군 | 사람이 Gemini에 웹 사용을 허용하는 참고 대상 | G-Web |
| 후보 카드 | 설명을 주장·근거·상태로 나눈 구조화 결과 | candidate card |
| 채점 전용 정답 | 후보에게 보이지 않는 정답·금지 주장·기대 상태 | scorer gold |
| 정당화 인증서 | 채점자가 소유하는 주장별 판정 근거 | justification certificate |
| 위험-포괄도 | 답한 비율과 그 답에서의 오류 비율을 함께 보는 지표 | risk-coverage |
| 내용 해시 | 입력이나 산출물이 바뀌지 않았음을 확인하는 짧은 값 | content hash |
| 실행 무효 | 비교 조건을 확인하지 못해 점수를 내지 않는 상태 | RUN_INVALID |
| 상태 변경 없음 | 다음 상태를 바꾸지 않는 명시적 결정 | NO_CHANGE |
| 심층 조사 | Gemini가 여러 자료원을 조사해 보고서를 만드는 기능 | Deep Research |
| 활동 보관 설정 | Gemini 대화 보관과 일부 연결 기능을 제어하는 설정 | Keep Activity |

## 1. 목적과 판정 범위

이 설계의 목적은 가격 변동 설명이 **근거 안에서만 말하는지**를 비교하는 것이다.
이 설계는 어느 서비스가 시장 움직임의 참된 단일 원인을 안다고 판정하지 않는다.

[저장소 사실] 제품 요구사항은 가격 반응을 해석 검증에만 쓰고 인과 증거로
표현하지 말라고 한다. 움직임 뒤에 공개된 사건은 원인 후보가 될 수 없다.
근거가 없으면 미설명으로 표시해야 한다.
`docs/product/requirements/price-explanation.md` L21–L29, L46–L54.

[저장소 사실] 설명 정당화 표준은 단일 사건 설명의 상한을 확정 인과가 아닌
확률적 귀속으로 둔다. 이 표준은 시점 고정, 근거, 반증 조건, 잔여 몫, 언어
강도를 연결한다.
`docs/engineering/design/explanation-justification-standard.md` L59–L104,
L116–L146.

[설계 결정] 본 비교의 허용 결론은 다음 셋으로 한정한다.

1. 같은 증거 묶음에서 어떤 군이 더 적은 지원 불가 주장과 누락을 냈는지.
2. 어떤 군이 근거·시점·상태 규칙을 통과하거나 위반했는지.
3. 자유 웹을 쓴 참고 결과가 끝에서 끝까지 어떤 모습인지.

[설계 결정] 다음 주장은 금지한다.

- Gemini 또는 우리 시스템이 가격의 참된 원인을 증명했다는 주장.
- 한 번의 Gemini 결과를 일반적인 Gemini 성능 또는 안정된 모델 성능으로
  일반화하는 주장.
- G-Web 결과를 O-PIT 또는 G-PIT-RAG의 공정 비교 점수에 섞는 주장.
- 이 벤치 통과를 사용자용 화면, 투자 조언 적합성, 가격 분해 완결성, 또는
  제품 출시 준비의 증명으로 부르는 주장.

[설계 결정] 결과에는 "근거 지원 가능성"만 적는다. 지원 가능성은 정해진
증거와 규칙이 허용하는지를 뜻한다. 이는 원인에 관한 외부 세계의 진실 판정이
아니다.

## 2. 현재 경계와 새 소유권

이 절은 기존 `view_explanation` 경계를 보존하고 새
`price_explanation` 제품 프로필의 소유권을 정한다.

[저장소 사실] 현재 `view_explanation` 벤치는 기존 일일 설명 경로를 감싸는
채점 계약이다. 이 벤치의 통과는 제품 요구사항, 최종 설명 산출물, 사용자 문장,
분해 합계, 재현성의 통과를 대신하지 않는다.
`docs/engineering/design/view-explanation-benchmark.md` L48–L68.

[저장소 사실] 기존 벤치는 자유 문단보다 구조화 후보 카드를 우선한다. 카드는
주장, 반대 근거, 데이터 공백, 종목 결정, 제안 상태 전이를 담는다.
`docs/engineering/design/view-explanation-benchmark.md` L154–L208.

| 소유 경계 | 소유하는 것 | 소유하지 않는 것 |
|---|---|---|
| `view_explanation` | 기존 경로의 후보 카드·정답 분리·상태 전이 채점 | 새 제품의 사용자 화면 품질과 Gemini 비교 결론 |
| `price_explanation` | 이 비교의 연구·감사 등급과 사용자 표시 등급 | 기존 `view_explanation` 실행 경로의 의미 변경 |
| 본 설계 문서 | 세 비교군, 수동 실행, 판정·보고 계약 | 실행 코드, 사례 파일, 시험 자료, 운영 설정 |

[설계 결정] `price_explanation`은 새 논리 제품 프로필이다. 이 이름은 이번에
새 파일이나 실행 경로를 만든다는 뜻이 아니다. 이 프로필은 아래 두 등급의
완료 주장을 서로 분리해 소유한다.

- **연구·감사 등급**은 후보 카드, 증거 묶음, 채점 전용 정답, 인증서, 사람
  판정, 실행 영수증을 검토할 수 있는 상태다.
- **사용자 표시 등급**은 연구·감사 등급을 통과한 결과를 실제 사용자 문장으로
  안전하게 표시할 수 있는 상태다.

[설계 결정] 연구·감사 등급의 통과는 사용자 표시 등급의 통과가 아니다.
사용자 표시 등급은 별도 제품 요구사항과 렌더링 검증을 통과해야 한다.

## 3. 비교군과 결과 위계

이 절의 시점 고정(PIT)은 각 사례의 기준 시각보다 늦게 알려진 정보를
입력이나 근거로 쓰지 않는 규칙이다.

| 비교군 | 입력과 실행 | 결과 지위 |
|---|---|---|
| 우리 시스템(O-PIT) | 엄격한 PIT 검색으로 증거 묶음 안에서만 후보 카드를 만든다 | 주 비교군 |
| Gemini 동일입력군(G-PIT-RAG) | 사람이 동일한 증거 묶음과 동일 지시문을 Gemini 웹 대화에 준다 | 주 비교군 |
| Gemini 자유웹군(G-Web) | 사람이 공통 사례 틀만 주고 Gemini의 자유 웹 사용을 허용한다 | 분리된 끝단 참고군 |

검색 증강 생성(RAG)은 주어진 자료를 찾아 답을 만들게 하는 방식이다.
G-PIT-RAG라는 이름은 Gemini가 증거 묶음만 참조한다는 뜻이다.

[설계 결정] O-PIT와 G-PIT-RAG는 같은 사례 식별자(`case_id`), 기준 시각,
초기 상태, 증거 묶음 바이트, 지시문 버전을 써야 한다. 단, 각 실행 환경에
필요한 형식 차이만 허용한다. 그 차이는 동일한 의미의 무손실 변환이어야 한다.

[설계 결정] G-Web에는 사례 식별, 관찰 구간, 기준 시각, 가격 관찰, 초기 상태,
출력 형식만 준다. G-Web에는 PIT 증거 묶음을 주지 않는다. 대신 웹에서 찾은
자료를 스스로 인용해야 한다. 이 차이 때문에 G-Web은 공정 비교가 아닌 끝단
참고군이다.

[설계 결정] 주 결과 표는 O-PIT와 G-PIT-RAG만 나란히 둔다. G-Web은 별도 표와
별도 문단으로만 보고한다. G-Web의 점수·사람 선호·비용을 주 비교군의 순위,
통과, 평균, 손실에 합치지 않는다.

[설계 결정] G-Web의 자유 웹 사용은 PIT 통과를 주장하지 않는다. 기준 시각을
넘는 자료를 쓰지 않았다는 별도 증명이 없으면 해당 항목은 `PIT 미평가`로
표시한다. 기준 시각 제약을 지켰다고 주장하면서 늦은 자료를 쓰면 PIT 하드 실패다.

## 4. 동일 입력과 출처 스냅샷 계약

이 절의 증거 묶음은 O-PIT와 G-PIT-RAG가 똑같이 보는 유일한 외부 사실 집합이다.

[설계 결정] 증거 묶음은 아래를 모두 포함한다.

- 사례 식별자, 관찰 구간, 기준 시각, 초기 상태와 버전.
- 관찰된 가격·분해 수치와 단위.
- 원문 증거의 식별자, 발행자, 공개 시각, 주소, 본문 또는 고정 사본.
- 각 증거가 기준 시각에 사용 가능했는지를 보이는 시각과 출처.
- 자료 묶음 버전과 전체 내용 해시.
- 후보에게 허용된 근거 식별자 목록.

[설계 결정] 증거 묶음에는 채점 전용 정답, 필수 주장, 금지 주장, 기대 상태,
사람 판정, 인증서 본문을 넣지 않는다. 후보 입력과 채점 전용 정답은 물리적·
형식적으로 분리한다.

[저장소 사실] 기존 벤치도 후보 입력과 채점 전용 정답을 분리한다. 채점 전용
정답이 후보 경로, 지시문, 어댑터, 심사 입력에 들어가면 벤치 자체를 무효로
처리한다.
`docs/engineering/design/view-explanation-benchmark.md` L231–L284.

[설계 결정] G-Web에서 응답이 웹 자료를 근거로 삼으려면, 운영자는 그 자료의
주소, 발행자, 제목, 접근 시각, 응답에 보인 인용 표기, 고정 사본 또는 사본 해시를
실행 영수증에 남긴다. 이 **출처 스냅샷 규칙**을 만족하지 못한 웹 근거는
증거 충실도에서 지원된 근거로 세지 않는다.

[설계 결정] 증거 묶음과 G-Web 출처 스냅샷에는 공개·비식별 자료만 넣는다.
개인 계정의 메일, 드라이브, 사진, 개인 파일, 비공개 거래 자료는 금지한다.

[INFERENCE] Gemini의 연결 앱과 사용자 화면은 계정 종류, 국가, 기기, 요금제에
따라 달라질 수 있다. 따라서 설정 상태는 추정하지 않고 실행 때마다 관찰해
영수증에 기록해야 한다. Google 도움말도 연결 앱의 제공 범위가 환경마다
달라질 수 있음을 설명한다.

## 5. Gemini 수동 실행과 영수증

Gemini는 수동 사용자 화면의 비교 대상이며, 자동 호출 가능한 고정 모델이 아니다.

[설계 결정] Gemini 실행에는 사람이 직접 사용자 화면을 조작한다. 브라우저
드라이버, 매크로, 문서 객체 모델 수집, 네트워크 수집, 화면 긁기, 계정·한도
우회, 자동 재시도는 금지한다. Gemini를 자동화하거나 긁어 모으거나 안정된
서비스 뒷단으로 취급하지 않는다.

[설계 결정] 모든 실행은 새 독립 대화로 시작한다. 이전 대화의 문맥, 재생성,
추가 질문, 초안 선택, 사람의 응답 수정은 금지한다. 응답 실패·한도·시간 초과는
품질 실패와 섞지 않고 실행 실패로 전수 기록한다. 더 좋은 응답을 고르기 위한
재실행은 금지한다.

[설계 결정] G-PIT-RAG 시작 전 운영자는 다음을 확인한다.

1. 심층 조사(Deep Research)를 선택하지 않는다.
2. 웹 검색 기능을 사용하지 않으며, 화면이 이를 끈 상태 또는 미선택 상태임을
   기록한다.
3. 모든 연결 앱을 끄고, 화면의 연결 앱 목록과 상태를 기록한다.
4. 증거 묶음만 붙이거나 붙여넣고, 그 밖의 파일·주소·대화를 넣지 않는다.
5. 화면에 검색 근거나 외부 인용이 나타나면 해당 실행을 G-PIT-RAG로 인정하지
   않고 무효로 기록한다.

[설계 결정] 사용자 화면이 웹 검색을 분명히 끌 수 없거나, 검색이 발생하지
않았음을 확인할 수 없으면 그 시도는 G-PIT-RAG가 아니다. 이 경우 결과를
G-Web으로 재분류하지 않는다. 실행 무효(`RUN_INVALID`)로 남기고 주 비교에서
제외한다.

[설계 결정] G-Web은 웹 검색과 자유로운 공개 웹 참조를 허용한다. 단, 연결 앱과
개인 자료는 계속 금지한다. G-Web도 동일한 구조화 후보 카드와 출처 스냅샷
규칙을 지켜야 한다.

Google의 공식 도움말은 심층 조사(Deep Research)가 기본적으로 Google Search를
자료원으로 포함하며, 추가 자료원을 고를 수 있다고 설명한다. 같은 도움말은
검색과 연결 자료를 쓰는 기능이 수동 확인 대상인 이유다.

[설계 결정] 실행 영수증에는 최소 다음을 남긴다.

| 항목 | 기록 내용 | 판정 용도 |
|---|---|---|
| 실행 식별 | 사례·비교군·반복 번호·운영자 가명 | 누락·중복 확인 |
| 시간 | 시작·응답 시각의 협정 세계시(UTC) | 순서·감사 확인 |
| 화면 조건 | 계정 종류·요금제·지역·언어·표시 모델명 | 환경 차이 공개 |
| 통제 확인 | 검색·심층 조사·연결 앱의 관찰 상태 | G-PIT-RAG 적격성 |
| 입력 | 지시문·증거 묶음·첨부물의 내용 해시 | 동일 입력 확인 |
| 원문 | 응답 전문·화면 인용·오류 표시 | 후보 카드 원본 |
| 출처 | G-Web의 출처 스냅샷 목록 | 증거 충실도 |
| 미노출 값 | 시드와 내부 버전은 미노출(`not exposed`)로 기록 | 추정 금지 |

[설계 결정] 영수증은 응답 직후 사람이 공식 복사 또는 내보내기 기능으로 보존한다.
임시 대화를 썼다면 다시 열 수 없을 수 있으므로 즉시 보존한다. 영수증에 개인
식별 정보가 보이면 공개본에서 가리되, 원본의 무결성 정보는 보존한다.

## 6. 후보 카드·정답·인증서 계약

이 절의 후보 카드는 세 비교군 모두가 직접 내야 하는 1급 산출물이다.
자유 문단은 후보 카드의 보조 표시일 뿐이다.

[설계 결정] 후보 카드는 최소 아래 필드를 가진다.

- 사례 식별자(`case_id`), 기준 시각(`asof`), 요약(`summary`), 보조 문단
  (`rendered_prose`).
- 주장 목록(`claims[]`): 주장 식별자, 주체, 술어, 대상 또는 값, 관찰 구간,
  주장 종류, 근거 식별자, 인용 문구, 확신 확률, 공백 여부.
- 반대 근거 목록(`counterpoints[]`)과 데이터 공백 목록(`data_gaps[]`).
- 종목 코드별 결정(`ticker_decisions[]`): 유지 또는 갱신 결정, 근거 주장,
  근거 식별자.
- 제안 상태 전이(`proposed_state_transition`): 이전 버전, 다음 적용일,
  다음 버전, 제안 상태.
- 입력 증거 묶음의 내용 해시(`input_packet_hash`)와 G-Web 출처 스냅샷 참조
  목록(`source_snapshot_refs[]`).

주장 종류는 관찰 사실(`OBSERVED`), 추정치(`ESTIMATED`), 가설(`HYPOTHESIS`) 중
하나다. 이 세 코드는 서로 바꿔 맞추지 않는다.

[설계 결정] 후보 카드가 없거나 응답 전문에서 주장·근거·결정을 사후 추출해야
하면 형식 하드 실패다. 채점자나 사람은 문단에서 숨은 주장이나 근거를 보완해
만들지 않는다.

[저장소 사실] 기존 벤치도 후보가 원자 주장을 직접 분해하도록 요구한다. 채점자는
문단을 의미 단위로 나누지 않으며, 금지 주장과 모순은 일반 점수보다 먼저 검사한다.
`docs/engineering/design/view-explanation-benchmark.md` L286–L311.

[설계 결정] 채점 전용 정답은 아래를 가진다.

- 필수·허용·금지 주장과 필요한 데이터 공백.
- 주장별 허용 근거와 증거 묶음의 시점 판정.
- 사례별 기대 결정과 다음 상태.
- 비교 시험의 변화·불변 규칙.
- 공개 여부, 층화 표지, 외부 검증 가능한 결과 라벨.
- 정당화 인증서 식별자와 적용 범위.

[설계 결정] 정당화 인증서는 채점자가 소유하는 불변 산출물이다. 인증서에는
인증서 식별자, 내용 해시, 정책 버전, 채점 기준 버전, 사례·주장·기준 시각의
적용 범위, PIT·근거·언어 판정이 있어야 한다. 후보는 인증서를 만들거나 자신이
통과했다고 선언할 수 없다.

[저장소 사실] 기존 벤치도 인증서를 후보가 아닌 채점자가 소유하게 하고, 적용할
수 없거나 찾을 수 없는 인증서 참조를 하드 실패로 처리한다.
`docs/engineering/design/view-explanation-benchmark.md` L210–L229.

## 7. 사례 층화와 공개·개발·봉인 분리

이 절의 사례 층화는 한 가지 쉬운 설명 유형에 맞춰 최적화하는 것을 막는다.

[설계 결정] 각 사례는 하나 이상 다음 층에 속한다.

| 사례 층 | 반드시 확인할 실패 또는 행동 |
|---|---|
| 새롭고 직접적인 근거 | 이른 공개 시각과 가격 관찰의 구분 |
| 근거 없음·미설명 | 억지 원인 대신 공백을 알리는지 |
| 동시 경쟁 가설 | 한 원인을 단정하지 않고 경쟁 근거를 남기는지 |
| 중복·재보도 | 기사 수를 새 근거 수로 부풀리지 않는지 |
| 시점 위반 유혹 | 늦은 공개 자료를 원인으로 쓰지 않는지 |
| 결측 자료 | 결측을 0이나 확정 사실로 바꾸지 않는지 |
| 상태 갱신 | 유지·갱신과 다음 상태를 정확히 제안하는지 |
| 가격 분해 불일치 | 가격 반응을 인과 증거로 승격하지 않는지 |

[설계 결정] 공개, 개발, 봉인은 사례의 노출 정책이다. 층과 노출 정책은 별개다.

| 구분 | 접근과 용도 | 결과 사용 |
|---|---|---|
| 공개 사례 | 증거·주석·판정 이유를 공개한다 | 교육·감사·회귀 점검 |
| 개발 사례 | 개발자가 볼 수 있는 공개 사례다 | 진단만 가능, 주 결과 아님 |
| 봉인 사례 | 사례·정답·사람 판정을 실행 전 숨긴다 | 주 비교의 최종 확인 |

[설계 결정] 모든 공개 사례에는 서로의 라벨을 보지 않는 독립 블라인드 전문가
두 명의 주석과 조정 판정이 필수다. 개발 사례도 공개 사례이면 같은 규칙을 따른다.

[설계 결정] 봉인 사례는 시점상 앞으로 진행된 자료로 만들고, 정답과 판정을
실행 전 고정한다. 같은 사건 계보, 정정·후속 기사, 재보도 묶음, 같은 다일
상태 궤적은 서로 다른 노출 구분에 나누지 않는다.

[설계 결정] 봉인 사례는 한 번 주 비교에 쓴 뒤 은퇴한다. 사례별 결과를 보고
지시문을 바꾸거나 후보를 고르는 데 쓰지 않는다. 봉인 자료가 준비되지 않았다면
주 비교의 결과는 차단하지 않음(`non-blocking`)이며 완료 주장을 할 수 없다.

[저장소 사실] 기존 벤치는 개발·봉인·사람 보류 구분을 두고, 같은 궤적과 사건
계보를 나누지 않는다. 봉인 결과는 사용 뒤 교체하며, 사람 보류 자료는 조정 전
튜닝에 쓰지 않는다.
`docs/engineering/design/view-explanation-benchmark.md` L354–L376.

## 8. 독립 주석과 조정 판정

이 절의 독립 주석은 각 전문가가 다른 전문가의 라벨과 비교군 이름을 보지 않고
판정하는 절차다.

[설계 결정] 공개 사례의 정답 작성은 다음 순서로 한다.

1. 두 금융·시장 미시구조 전문가가 증거 묶음만 보고 독립적으로 주장, 공백,
   허용 근거, 금지 언어, 기대 상태를 라벨링한다.
2. 두 사람의 원 라벨, 근거 메모, 라벨 버전을 변경 불가 기록으로 보존한다.
3. 조정자는 불일치를 사례 단위로 해결하고, 선택한 근거와 기각한 해석을 적는다.
4. 조정된 결과만 채점 전용 정답과 인증서에 넣는다.
5. 합의가 불가능하면 사례는 모델 실패가 아니라 주석 기준 문제로 표시한다.
   해당 사례는 주 비교의 통과 근거로 쓰지 않는다.

[설계 결정] 사람 비교 평가는 세 비교군 이름을 가린 채 수행한다. 카드와 보조
문단은 무작위 순서로 제시한다. 사람은 사실성, 근거 연결, 인과 절제, 공백의
정직성, 상태 결정을 따로 평가한다. 모델 이름이나 말투는 평가 항목이 아니다.

[설계 결정] 주석 일치도는 사전에 고정한 라벨 기준과 최소 사례 수를 보고한다.
일치도가 기준보다 낮으면 사람 평가 관문은 무효다. 낮은 일치도는 어느 군의
자동 통과가 아니다.

NIST의 AI 위험·영향 평가 보고서는 훈련, 평가, 조정의 분리와 불일치를 기준
개선 신호로 다룬 사례를 제시한다. 이 설계는 그 원칙을 공개 사례의 주석 절차에
적용한다.

## 9. 하드 실패와 비거래 규칙

이 절의 하드 실패는 다른 점수로 상쇄할 수 없는 실패다. 하드 실패가 하나라도
있으면 그 사례·반복·군은 품질 통과가 아니다.

| 하드 실패 | 발생 조건 | 처리 |
|---|---|---|
| 형식 | 후보 카드가 없거나 필수 필드가 없다 | 즉시 실패 |
| PIT | PIT를 주장한 군이 늦은 자료를 쓴다 | 즉시 실패 |
| 증거 | 주장이 허용 증거나 출처 스냅샷으로 연결되지 않는다 | 즉시 실패 |
| 날조 | 인용·수치·출처·사실을 증거가 말하지 않는데 만들었다 | 즉시 실패 |
| 금지 언어 | 인증서보다 강한 인과·확신 언어를 쓴다 | 즉시 실패 |
| 상태 발산 | 기대한 다음 상태와 한 항목이라도 다르다 | 즉시 실패 |

[설계 결정] PIT 하드 실패는 O-PIT와 G-PIT-RAG의 필수 관문이다. G-Web은 PIT를
통과했다고 주장하지 않는 한 `PIT 미평가`다. G-Web의 증거, 날조, 금지 언어,
상태 발산은 다른 군과 동일하게 하드 실패다.

[설계 결정] 상태를 바꾸지 않는 사례도 상태 변경 없음(`NO_CHANGE`)을 명시해
채점한다. 상태 사례가 없는 결과 묶음은 상태 정확성을 입증하지 못하므로
주 비교 통과를 주장할 수 없다.

[저장소 사실] 기존 벤치는 어떤 상태 발산도 허용하지 않고, 하드 실패가 있으면
다음 상태로 승격하지 않는다. 금지 규칙을 검사할 수 없으면 후보가 아니라 벤치
자체를 무효로 본다.
`docs/engineering/design/view-explanation-benchmark.md` L378–L403,
L614–L632.

[설계 결정] 하드 실패는 평균, 가중 손실, 사람 선호, 유창성, 비용, 응답 길이로
상쇄할 수 없다. 이는 PIT·증거·날조·금지 언어·상태 발산 모두에 적용한다.

## 10. 지표와 이차 손실

이 절의 지표는 하드 실패가 없는 사례에서만 계산한다. 먼저 사례별 값을 만들고,
그 뒤 사례 층별 평균과 거시 평균을 낸다. 전체 합산 비율은 진단용으로만 쓴다.

| 지표 | 계산 | 해석과 제한 |
|---|---|---|
| 위험-포괄도 | 확신 임계값마다 답한 주장 비율과 그 주장 오류 비율을 함께 보고 | 높은 포괄도만으로 좋다고 하지 않음 |
| 거짓 공백 정밀도 | 올바른 공백 선언 수 ÷ 모든 공백 선언 수 | 1에서 뺀 값은 근거가 있는데 공백이라 한 비율 |
| 필수 주장 재현율 | 맞춘 필수 주장 수 ÷ 모든 필수 주장 수 | 모든 것을 공백으로 말하는 회피를 막음 |
| 증거 충실도 | 지원된 주장-근거 연결 수 ÷ 모든 주장-근거 연결 수 | 주 비교는 증거 묶음, G-Web은 출처 스냅샷을 기준으로 함 |
| 상태 정확성 | 정확한 다음 상태 수 ÷ 채점 가능한 상태 사례 수 | 동시에 상태 발산 건수도 보고 |
| 외부 검증 보정 | 사전 지정한 외부 결과 라벨이 있는 주장에만 확신 확률을 검증 | 인과 귀속의 진실 보정으로 부르지 않음 |

위험-포괄도에서 위험은 사람 조정 정답이 지원하지 않는 답의 비율이다.
포괄도는 답 또는 채택을 선택한 주장 비율이다. 이 지표는 절제와 유용성을 함께
보이며, 원인 진실을 직접 재는 지표는 아니다.

외부 검증 보정은 결과 출처, 결과 확인 시각, 사례 적용 범위를 미리 정한 경우에만
계산한다. 브라이어 점수(Brier score)나 신뢰도 표는 이 경우에만 보고할 수 있다.
인과 귀속에는 관찰 가능한 참·거짓 라벨이 없으므로, 사람의 지원 수용 판정은
`지원 수용 보정`으로 분리해 표기한다.

[저장소 사실] 기존 벤치도 외부 결과 출처와 시각이 있는 주장에만 보정을 계산하고,
인과 귀속에 진실 보정을 적용하지 않는다.
`docs/engineering/design/view-explanation-benchmark.md` L435–L466.

[설계 결정] 보조 손실은 하드 실패가 전혀 없는 비교에서만 아래처럼 보고한다.

$$
L = 0.6 \times \text{거짓 인과 귀속률}
  + 0.4 \times \text{중요한 지원 설명 누락률}
$$

말로 하면: 거짓 인과 귀속을 중요한 지원 설명의 누락보다 더 무겁게 본다.

[설계 결정] 이 0.6:0.4 손실은 두 실패의 상대적 진단 비중일 뿐이다. 이는
통과 점수도, 하드 실패의 보상 수단도, 모든 지표를 하나로 숨기는 순위도 아니다.

## 11. 반(反) 굿하트 대비 시험

이 절의 굿하트 현상은 점수만 맞추고 실제 계약을 피하는 행동이다.

[설계 결정] 모든 고위험 층에는 원 사례와 최소 변경 사례를 쌍으로 둔다.
`MUST_CHANGE`는 변경된 증거에 따라 답이 반드시 바뀌어야 함을 뜻한다.
`MUST_NOT_CHANGE`는 무관한 변경에도 답이 바뀌면 안 됨을 뜻한다.

| 대비 시험 | 변경 | 기대 관계 |
|---|---|---|
| 시점 교환 | 핵심 사건의 공개 시각을 기준 시각 뒤로 옮김 | 원인 주장은 MUST_CHANGE로 사라지거나 공백이 됨 |
| 근거 제거 | 유일한 직접 근거를 증거 묶음에서 뺌 | 그 근거를 인용한 주장은 MUST_CHANGE |
| 재보도 추가 | 같은 사건의 중복 기사를 더 넣음 | 주장 수·확신이 MUST_NOT_CHANGE |
| 경쟁 근거 삽입 | 같은 창의 반대 방향 근거를 추가 | 단정 언어는 MUST_CHANGE로 약해지거나 경쟁 가설을 냄 |
| 공백 유혹 | 필수 근거는 유지하고 공백 선언만 추가 | 공백 정밀도와 필수 주장 재현율이 회피를 잡음 |
| 상태 오염 | 갱신 근거를 무효화하거나 다음 상태를 바꿈 | 유지·갱신과 다음 상태가 MUST_CHANGE |
| 인용 훼손 | 인용 주소 또는 스냅샷 내용을 바꿈 | 증거·날조 하드 실패가 발생 |

[설계 결정] 이 대비 시험은 현실 세계의 인과 개입을 흉내 냈다고 주장하지 않는다.
이 시험은 입력의 작은 의미 변화에 결과가 계약대로 변하는지 보는 출력 충실도
시험이다.

## 12. 보고와 사람 검토

이 절의 보고는 어떤 조건에서 나온 비교인지 재현 가능하게 밝히는 감사 산출물이다.

[설계 결정] 주 비교 보고서는 O-PIT와 G-PIT-RAG에 대해 다음을 함께 제시한다.

- 사례·층·노출 구분별 분모와 제외 사유.
- 하드 실패 종류와 건수. 하드 실패가 있으면 품질 통과는 거짓이다.
- 위험-포괄도 곡선, 거짓 공백 정밀도, 필수 주장 재현율, 증거 충실도,
  상태 정확성, 외부 검증 보정.
- 0.6:0.4 보조 손실의 두 성분과 합계.
- 사람의 독립 판정 수, 조정 수, 일치도, 보류 사례 수.
- 증거 묶음·정답·인증서·지시문·실행 영수증의 버전과 해시.

[설계 결정] G-Web 보고서는 별도 제목과 분모를 쓴다. G-Web에는 웹 출처
스냅샷 완결성, PIT 미평가 수, 하드 실패, 같은 품질 지표를 표시할 수 있다.
그러나 G-Web을 주 비교의 우승·비열세·출시 관문에 사용하지 않는다.

[설계 결정] 사람 검토는 자동 지표가 통과한 뒤의 별도 관문이다. 두 전문가가
가려진 군의 카드와 문단을 독립 평가하고 조정한다. 사람 검토는 형식, PIT,
증거, 날조, 금지 언어, 상태 하드 실패를 대신하지 않는다.

[저장소 사실] 기존 벤치도 사람 심사와 자동 하드 관문을 분리하고, 낮은 평가자
일치도를 자동 통과가 아닌 사람 관문 무효로 처리한다.
`docs/engineering/design/view-explanation-benchmark.md` L480–L561.

## 13. Phase 0 데이터 우선 실행 순서

이 절의 Phase 0은 모델 지시문, 자동 채점기, 사용자 화면보다 먼저 사례와 근거를
확정하는 단계다.

[설계 결정] 실행 순서는 아래와 같다.

1. 공개·개발·봉인 정책과 사례 층의 목표 분포를 고정한다.
2. 가격 관찰과 원문 증거를 수집하고, 각 자료의 사용 가능 시각을 확정한다.
3. 증거 묶음과 출처 스냅샷을 고정하고 해시를 만든다.
4. 두 독립 전문가가 공개 사례를 주석하고 조정한다.
5. 채점 전용 정답과 정당화 인증서를 버전·해시와 함께 고정한다.
6. 하드 실패 규칙과 대비 시험이 실제로 채점 가능한지 검토한다.
7. O-PIT의 후보 카드 출력과 Gemini 수동 실행 영수증을 작은 공개 사례에서
   점검한다.
8. 봉인 사례를 잠그고, 그 뒤에만 주 비교를 실행한다.
9. 연구·감사 보고를 먼저 검토하고, 그 뒤에만 사용자 표시 등급을 별도로 검토한다.

[설계 결정] Phase 0에서 증거·주석·정답·인증서 중 하나라도 빠지면 비교 실행을
시작하지 않는다. 이 상태는 후보의 낮은 점수가 아니라 벤치 무효다.

## 14. 단계별 완료 주장

이 절은 무엇을 완료라고 부를 수 있는지를 제한한다.

| 단계 | 허용되는 완료 주장 | 아직 주장할 수 없는 것 |
|---|---|---|
| 설계 | 세 비교군과 안전 규칙이 문서로 고정됨 | 사례·실행·성능이 준비됨 |
| Phase 0 완료 | 감사 가능한 공개 사례와 봉인 정책이 준비됨 | 비교군 우열 또는 사용자 표시 준비 |
| 연구·감사 완료 | 봉인 주 비교, 하드 관문, 사람 조정, 영수증이 모두 충족됨 | 사용자용 문장 또는 투자 조언 준비 |
| 사용자 표시 완료 | 별도 제품·렌더링 검증까지 통과함 | Gemini 결과의 일반 성능 주장 |

[설계 결정] 이 문서는 설계 단계만 완료한다. 이 문서는 실행 자료, 주석, Gemini
세션, 자동 채점기, 시험 결과를 만들거나 주장하지 않는다.

## 15. 남는 위험과 의도적 보류

- Gemini 사용자 화면의 검색 통제는 계정과 화면 조건에 따라 검증 가능성이 다를 수
  있다. 검증할 수 없는 G-PIT-RAG 시도는 무효로 처리한다.
- G-Web은 실제 웹 탐색 능력을 포함하므로 동일입력 비교가 아니다. 이 차이는
  제거하지 않고 분리 보고한다.
- 단일 사례의 인과 진실에는 외부 참·거짓 라벨이 없을 수 있다. 그래서 인과
  주장에는 지원 수용 판정만 적용하고 진실 보정을 주장하지 않는다.
- 공개 사례가 충분히 많지 않거나 전문가 일치도가 낮으면 사람 관문은 보류한다.
  이를 모델의 자동 통과로 바꾸지 않는다.
