# Sync 프로토콜 계약 (확정 결정)

> **계약 문서** — 이 파일의 변경은 진기·영서 공동 승인 대상이다(CODEOWNERS). 인터페이스 계약의 정의는 [event-bundle-schema.md](event-bundle-schema.md).

**MVP 구현 스펙**:

- **Cursor**: 테넌트별, Cloud 서버가 발번하는 단조 증가 sequence. Sync Agent는 마지막 처리 cursor를 로컬 저장하고 `?after={cursor}`로 Pull.
- **Cursor 발번 시점 (확정, 2026-07-13)**: 공통 이벤트는 비개인화 단일 레코드지만 cursor는 테넌트별이므로, **테넌트별 outbox fan-out 시점**(공통 이벤트 1건 → 테넌트별 전달 레코드 N건 생성)에 각 테넌트의 sequence를 발번한다. Event Bundle은 이 outbox를 cursor 순으로 묶어 생성한다. 이 fan-out 규칙은 "Cloud Event Store 스키마 + 번들 생성 규칙" 인터페이스 계약([event-bundle-schema.md](event-bundle-schema.md))의 일부이므로 변경 시 진기-영서 양자 합의 대상.
- **전송 단위**: Event Bundle (신규 이벤트 + 정정 이벤트 + 무효화 이벤트 포함).
- **무결성**: 번들 단위 SHA-256 체크섬. 검증 실패 시 저장하지 않고 재시도.
- **폴링 주기**: 기본 1~5분 (테넌트 설정 가능).
- **전달 보장**: at-least-once. On-Prem 저장은 이벤트 ID 기반 **멱등 upsert** — 중복 수신은 무해해야 한다.
- **순서**: cursor 순 처리. 서버 발번 단조증가 cursor를 순차 소비하므로 정정/무효화는 항상 대상 원본 이벤트보다 늦게 도착한다 (원본 cursor < 정정 cursor). 정정/무효화 이벤트는 대상 원본 이벤트 ID를 참조한다. "원본 미수신 상태의 정정"은 gap(sequence 누락)에서만 발생할 수 있으므로, 보류-재처리 로직은 gap 감지(목표 계약)와 함께 도입한다. MVP는 순차 소비 보장 하나로 순서를 담보한다. (참고: 서버 발번 sequence 구조에서는 gap 감지가 수신 cursor의 불연속 확인만으로 가능해 구현 비용이 낮다 — walking skeleton 안정화 후 목표 계약에서 MVP로 조기 승격 검토 후보.)

**목표 계약 (문서상 명시, 구현은 후순위)**:

- MVP 스펙 + **벤더 개인키 기반 번들 서명** — 감사 시 "이 콘텐츠는 벤더가 발행한 원본"임을 증명. Raw Event Store에 서명 원본 보존.
- 순서 보장 및 gap 감지(sequence 누락 시 재요청)의 명시적 계약화.

## Tenant Sync API 엔드포인트 계약

> **상태: 초안 (ALPHA-356, 2026-07-15)** — `[합의 필요]` 표기 항목은 합의 세션에서 확정.

**엔드포인트** (mTLS 필수, 인증서-테넌트 바인딩을 매 요청 인가 검증 — [sync-auth.md](sync-auth.md)):

```
GET /api/v1/sync/bundle?after={cursor}&limit={n}
```

- `after`: 마지막 처리 cursor (첫 동기화는 `0`). `limit`: 엔트리 수 상한, 기본 100·최대 500.
- 테넌트 식별은 쿼리/경로에 없다 — **인증서 바인딩에서만 도출**한다 (파라미터로 받으면 인가 검증과 별개의 신뢰 입력이 생긴다).

**응답** — 항상 번들 0~1개 (요청당 다중 번들 없음. 단순성 우선, 배압은 `limit`과 폴링 주기로):

| 상황 | 응답 |
|---|---|
| 신규 엔트리 있음 | `200` + Event Bundle JSON ([event-bundle-schema.md](event-bundle-schema.md)) + `X-Bundle-Checksum` 헤더 |
| 신규 없음 | `204` (body 없음) |

- 다음 요청의 `after`는 응답 번들의 `cursor_to`다. 별도 `next_cursor` 필드를 두지 않는다.
- `cursor_to`까지 **처리(저장) 완료 후에만** 로컬 cursor를 전진한다 — at-least-once의 소비자측 규율.

**에러 시맨틱**:

| 코드 | 의미 | Sync Agent 동작 |
|---|---|---|
| 401 | 인증서 무효(만료·해지) | 재시도 불가 — 연결 상태 오류로 표면화, 인증서 교체 플로우 |
| 403 | 인증서-테넌트 바인딩 불일치 | 재시도 불가 — 즉시 오류 표면화 (구성 오류) |
| 410 | `after`가 retention 밖 (outbox 정리로 소실) | full resync 경로 진입 `[합의 필요 — resync 절차는 outbox retention과 함께 확정]` |
| 429 / 5xx | 일시 장애 | 지수 백오프 재시도 (폴링 주기 내) |

- 400번대 중 401·403·410 외에는 계약 위반(버그)으로 간주 — 재시도하지 않고 오류로 표면화한다(fail-loud).

**규모 가정 (설계 입력)** `[합의 필요 — 아래는 초안 가정치, 파이프라인 실측으로 검증]`:

- MVP 커버리지 국내 상장 ETF(약 9백여 종목) 기준 **일일 공통 이벤트 ≤ 2,000건** (장중 변동 이벤트 + 정정·무효화는 그 1% 미만).
- 테넌트별 outbox 증가 = 공통 이벤트 수와 동일 (전 이벤트 fan-out 기준). 엔트리당 페이로드 ~수 KB → 번들 최대 500엔트리 ≈ 수 MB, 기본 폴링 1~5분에서 한 번들이면 충분.
- 이 가정이 10배를 넘으면 `limit` 기본값과 폴링 주기를 재검토한다 (프로토콜 구조 자체는 불변).
