## 내 가설이 틀렸던 것

- `search_objects` 2회 이하: 회사를 찾은 뒤 그 회사 ID로 주식을 찾는 세 번째 호출은 발행 관계를 따라간 올바른 조회였다. 이 경로는 `get_linked_objects`가 들어온 뒤 관계 조회로 바뀌었다.
- 비중을 저장된 자릿수 그대로 답한다: 24.22%를 24.2%로 쓰는 것은 반올림이지 환산이 아니다. 기준을 고쳤다.
- 구성 나열 질문에는 합계 도구를 부르지 않는다: 답에서 합계를 언급할 때 도구로 계산하는 것이 의도한 동작이다. 가설을 뺐다.

## 풀지 못한 것

- **없는 것을 확인하는 질문에서 검색이 20~35회로 늘어난다** (P-LO-1 "보통주 말고 더 있는지", 입력 최대 62만 토큰). 에이전트는 관계 조회를 맞게 한 뒤, 주식 자료에 우선주가 아예 없다는 것을 알아내려고 다른 종목·다른 자료 종류를 계속 찾는다. 판단 자체는 타당하다. 실제로 주식 자료에는 보통주만 있다. 도구 응답 문구로는 멈추지 않았다. 엔진의 조사 규칙(`prompts/research.md`의 "빈 검색은 구조적 한계가 아니다")과 맞물린 문제라 도구 범위 밖이다.
- **도구가 늘수록 같은 질문의 탐색이 넓어진다.** 코드 확인 질문은 도구가 2개일 때 입력 1.2만 토큰, 9개일 때 1.5만 토큰이다. 도구 설명이 프롬프트에 실리는 비용이다.

## 열린 문제

- 실행기는 그래프 도구만 가진 에이전트를 돌린다. 엔진의 기존 DB 도구와 함께 있을 때의 선택은 아직 확인하지 않는다.
- `get_etf_holdings`는 엔진의 기존 도구를 대체하지 못한다. 수집 완전성 상태가 뷰에 없다 (뷰 기록 참조).
- 그래프 연결이 긴 실행 중 끊긴 적이 있다("defunct connection"). 실행마다 연결을 새로 여는 것으로 피했다.
- `src/uv.lock`에 `neo4j` 추가와 무관한 `sys_platform != 'emscripten'` 마커 변경이 섞여 있다. 로컬 uv가 다시 쓴 것이다.
