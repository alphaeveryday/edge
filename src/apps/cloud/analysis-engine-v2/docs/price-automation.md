# 가격변동 자동 실행

기존 설명 큐의 사건을 v2가 접수하고, SFN이 분석을 실행합니다. 완료된 설명과 근거는 기존 금융사 전달 경로를 통해 자동 게시합니다. 적재·가격 판정·큐는 변경하지 않습니다.

## 실행과 복구

- API·가격 사건·전망이 호출하는 단건 SFN에서 실행 자리를 확보한 뒤 Fargate를 시작합니다.
- 공통 상한은 기존 `analysis_slots` 설정(1~3개)을 따릅니다. 같은 종류·ETF는 순서대로 처리합니다. 대기는 SFN에서 30초마다 확인합니다.
- 자리는 실행 ARN으로 소유합니다. 정상·실패 종료 시 해제합니다. 반납 없이 끝난 실행의 자리는 다음 요청이 그 실행의 태스크가 멈췄다는 근거를 확인한 뒤 회수합니다. 근거는 실행 이력의 `STOPPED` 기록이나 ECS의 `STOPPED` 응답뿐입니다. 실행이 RunTask를 부르기 전에 끝났다면(이력에 호출이 없음) 태스크가 없으므로 회수합니다. 남은 태스크는 종료를 요청합니다.
- 근거가 부족한 자리는 점유로 남아 상한에 포함되고 같은 종류·ETF의 새 실행을 막습니다. ECS가 태스크를 찾지 못함(`task-missing`), RunTask를 불렀지만 태스크가 기록되지 않음(`task-unrecorded`), 조회 실패(`task-state-unknown`, `check-failed:*`)가 여기에 듭니다. 시간이 지나도 저절로 풀리지 않습니다. 그 판정이 실패해도 다른 자리 확보는 계속되고, 남은 자리와 사유는 자리 확보 결과의 `held`와 실행 제어 Lambda 로그(`Keeping analysis slot occupied`)에 남습니다.
- 남은 자리의 수동 복구: ① `aws stepfunctions describe-execution --execution-arn <실행 ARN>`으로 그 실행이 끝났는지 확인합니다. ② 그 실행의 태스크(자리 행의 `task_arns`, 비어 있으면 실행 이력의 `TaskSubmitted`)마다 `aws ecs describe-tasks --cluster <분석 클러스터> --tasks <ARN>`이 `STOPPED`를 답하는지 봅니다. ECS는 멈춘 태스크를 적어도 1시간 보여 주므로 경고를 본 뒤 바로 확인합니다. ECS 목록에 없음, `MISSING`, 로그 끊김, 워커 manifest의 완료 기록은 태스크가 멈췄다는 기록이 아닙니다. ③ 모든 태스크의 `STOPPED`를 확인한 자리만 writer 연결로 `DELETE FROM analysis_execution_slots WHERE execution_arn = '<실행 ARN>'`합니다. 확인하지 못하면 지우지 않고 원인을 조사합니다.
- 분석 오류를 성공으로 처리하지 않습니다. 실패한 모델 실행은 원본 기록을 보존합니다. 이미 완료된 분석의 전달 재시도는 모델을 다시 호출하지 않습니다.
- 같은 사건 재전달은 같은 실행에 연결합니다. SFN 접수와 DB 기록이 모두 확인된 뒤 SQS 메시지를 삭제합니다.
- 워커는 단건 SFN의 실행 ARN을 받아, 발행 트랜잭션에서 자기 자리 행을 잠근 채 새 결과를 커밋합니다. 자리가 이미 회수됐으면 발행하지 않고 실패로 남깁니다. 전달 등록은 커밋된 발행만 대상으로 하므로 따로 자리를 확인하지 않습니다. 모델 대기 중에는 DB 연결을 쥐지 않고, 끊긴 연결은 같은 시도 안에서 다시 엽니다.

## 회수와 교대

- `ExposureReverted`는 원본 outbox와 대조하고, 종목·세션·복귀 시각을 저장합니다. 그 시각 이전 설명만 회수합니다.
- 회수 뒤 끝난 과거 분석은 새로 게시하지 않습니다. 이후 재발화한 설명은 허용합니다.
- 회수는 가격 사건에서 생성된 설명을 대상으로 합니다. 수동 API 요청·전망·다른 거래 세션의 과거 게시물은 회수하지 않습니다.
- 회수된 설명은 최신 조회에서 제외하고, 분석 ID로 조회하는 이력과 근거는 보존합니다.
- v1 소비자를 정지하고 진행 중 작업이 끝난 뒤 같은 ECS 서비스에서 v2 소비자를 시작합니다. 두 버전이 같은 큐를 경쟁 소비하지 않습니다.
- 실제 사건의 자동 게시·재전달·회수 확인 이후 전환 완료로 기록합니다.

## 최초 전환과 이후 배포

- 최초 전환: v1 서비스의 실행 태스크와 큐 처리 중 메시지가 0인지 확인 → v2 소비자 태스크 정의로 같은 서비스를 변경합니다.
- 서비스는 기존 큐 기반 자동 확장(0~4대)을 유지합니다. 분석 대기는 SFN에서 처리하고 실행할 때만 Fargate를 띄웁니다.
- 이후 코드 배포: API·분석 워커·실행 제어 Lambda·v2 소비자를 함께 갱신합니다. 소비자가 아직 v1이면 자동 교체하지 않습니다.
- 실패·시간 초과·중단은 기존 운영 알림 대상으로 전달합니다. 모델 실패를 성공으로 바꾸거나 무제한 재호출하지 않습니다.
- 전환 검증 실패 시 신규 접수를 멈추고 진행 중 v2 실행을 확인한 뒤 기존 v1 태스크 정의로 되돌립니다. 두 소비자를 동시에 실행하지 않습니다.
  - v1으로 되돌리거나 v1을 수동 실행하기 전에 2026-10-02 5분봉 문제(ALPHA-1153)를 확인합니다. `canonical/market_data/intraday_5m/market=KR/trade_date=2026-10-02/part-0.parquet`의 14:30~15:05 8개 버킷은 1분 22개 창이 빠진 채 만든 부분본입니다. v1은 5분봉의 분 수를 모르고 준비 여부를 날 단위로만 보므로 이 결손을 알아채지 못합니다. 10-02와 다음 거래일(10-06, 전일 β)을 대상으로 v1을 실행하면 이 값이 그대로 쓰입니다. v2는 5분봉을 읽지 않습니다.
  - 설명 큐 DLQ에 남은 10-02 미처리 6건은 분석이 생성되지 않은 건입니다. 재처리 승인 없이 redrive하거나 삭제하지 않습니다.
- 전망의 분석 내용·일정은 변경하지 않습니다. 공통 SFN의 동시 실행 제한만 함께 적용됩니다.

- 사건의 원본 JSON은 정확히 대조합니다. 원본 수치와 가격 트리거 테이블의 비교는 DB 정밀도(가격 6자리·비율 8자리)의 반올림을 적용합니다.
