# 연구 하네스의 단계별 검증

각 단계는 의도 → 실패 재현 → 최소 변경 → 같은 시험 재실행 → 원인 확인 순서로 수행한다. 하나의 단계가 통과하기 전 다른 행동 개선을 섞지 않는다. 기계적 통과와 실제 모델의 분석 품질을 구분한다.

## 1. 질문을 등록하지 않은 분석의 완료 방지

의도: 분석 모델이 조사할 질문을 작업 목록에 명시한 뒤 조사하도록 한다. 빈 작업 목록을 완료로 취급하지 않는다.

통과 기준:
- 목록 없이 분석 도구나 StructuredOutput을 호출하면 질문 등록을 요구한다. 지침·스킬·초기 자료 읽기와 작업 등록은 허용한다.
- 도구 없이 종료하는 경우에도 runner가 후속 실행을 요청하고, 계속 등록하지 않으면 미완료로 실패한다.
- 빈 목록으로 기존 질문을 지울 수 없다.
- 실제 DeepSeek의 고정 자료 시험에서 첫 분석 도구 실행 전 질문을 등록하고 기존 정답·출처 검사를 통과한다.

기존 문제의 원인: 지침은 비단순 작업만 목록 작성을 요구했고, 구현은 등록된 미완료 항목이 없으면 완료로 처리했다. 앞선 Flash·Pro 고정 자료 실행은 작업 목록 없이 완료됐다.

이번 단계에서 증명하지 않는 것: 등록된 질문의 완전성, 근거 없는 완료 표시의 탐지, 모든 중요 질문의 재귀 탐구, 투자 분석 품질의 일반적 향상. 이들은 각각 별도 실패 사례와 최소 개선으로 검증해야 한다.

검증 경과:
1. 수정 전 빈 목록 완료·등록 전 도구 허용·빈 목록 교체를 재현하는 테스트 4개가 실패했다.
2. 비어 있지 않은 질문 등록을 프리훅과 종료 경계에서 요구한 후 관련 테스트 30개가 통과했다. 전체 회귀는 당시 456개 통과, 생략 없음이었다.
3. 첫 실제 Flash 실행은 질문을 등록했지만 원자료 조회의 subject를 69회 추측하며 반복했다. 평가자가 중단했으며 통과로 처리하지 않았다. 해당 프로세스 종료는 확인했다. 강제 중단으로 남은 임시 작업 폴더의 삭제는 자동 승인 검토에서 정책상 차단돼 수행하지 못했다. 원래 실행 로그와 실패 기록은 유지했다.

## 1-1. 질문 등록 시험을 막은 원자료 조회 인터페이스 수정

원인: 목록형 자료는 subject=""로 조회해야 했지만 subject를 필수 문자열로 노출했고, 도구 설명과 오류 응답에 이 규칙이 없었다. 모델에게 조회 실패의 올바른 수정 경로를 제공하지 못했다.

최소 변경: source만으로 조회할 수 있도록 subject·offset·limit에 기본값을 주고 선택 필드로 노출한다. 잘못된 subject에는 생략 방법 또는 실제 키 목록을 알려준다. 관련 재현 테스트의 실패를 확인한 후 수정했고 관련 테스트 32개가 통과했다.

같은 공개 자료를 다시 실행한 결과 질문 등록 선행·등록 항목 완료·공개 대안 조회·정답·근거 ID·IR 인용 여섯 검사가 모두 통과했다. 결론은 같은 매출에 마진이 낮아지므로 이번 분기 이익 감소였다. 분석 도구 11회(뉴스 1, 웹 검색 6, 원문 읽기 4)를 사용했다. 단일 실행이므로 효율이나 일반적 분석 품질 향상을 입증하지 않는다.

반대 사례인 비공개 자료도 실제 Flash로 실행해 여섯 검사가 모두 통과했다. IR에 기록된 비공개·계약상 제한을 확인했고 이익 방향을 꾸며내지 않았다. 분석 도구는 20회(뉴스 4, 웹 검색 9, 원문 읽기 7)였다. 두 성공 실행의 초기 원자료 조회는 각각 3회·4회였으며 모두 source만 지정해 성공했다. 두 임시 작업 폴더는 정상 종료 후 제거됐음을 확인했다.

최종 회귀: 457개 통과, 생략 없음. 변경은 로컬 작업 트리에 있으며 머지·배포하지 않았다. 이번 단위의 등록·조회 통과를 전체 딥리서치 구조의 완료로 표시하지 않는다. 다음 검증 대상은 등록한 질문의 누락·부당한 완료이며, 별도 실패 사례를 먼저 정의해야 한다.

## 1-2. Arcade 원칙으로 입력 선택과 오류 복구 재검토

앞선 수정은 필수 인자를 줄였지만 자료 이름을 여전히 임의 문자열로 받았고 오류를 문장만으로 반환했다. 다음 원칙을 현재 SDK에 적용했다. Arcade 서버나 새 런타임을 설치한 변경은 아니다.

| 원칙 | 적용 |
|---|---|
| [Constrained Input](https://www.arcade.dev/patterns/constrained-input/) | 실행별 실제 source 목록을 도구 스키마 enum으로 노출하고 서버에서도 검증한다. |
| [Recovery Guide](https://www.arcade.dev/patterns/recovery-guide/) | 실패한 필드·원인·수정 가능 여부·실제 허용 값 또는 다음 호출 인자를 구조화해 반환한다. |
| [Error Classification](https://www.arcade.dev/patterns/error-classification/) | 잘못된 입력, 정상적인 빈 자료, 내부 실행 오류를 구분한다. 내부 오류를 입력 수정으로 해결할 수 있다고 오표시하지 않는다. |
| [Tool Adapter](https://www.arcade.dev/patterns/tool-adapter/) | 자료 종류에 따른 처리는 코드가 맡고, 원자료 조회의 필수 입력은 source 하나로 유지한다. |

첫 실패 재현: 실제 source만 선택되는지와 오류 응답으로 바로 복구할 수 있는지에 관한 4개 테스트가 기존 구현에서 실패했다. 구조화된 SourceInputError와 입력 enum을 적용한 뒤 통과했다. 빈 자료·잘못된 타입·내부 오류의 분리도 검증했다.

실제 SDK + DeepSeek Flash 시험:
- 목록형 news: 잘못된 subject를 한 번 입력하게 했다. 오류의 retry_arguments를 사용한 다음 호출에서 원문을 읽었고 정확한 제목을 반환했다.
- 사전형 prices: 잘못된 종목 키를 한 번 입력하게 했다. 다음 호출에서 자료 목록을 읽고 실제 키 NOVA로 세부 조회해 정확한 종가를 반환했다. 추가 오류는 없었다.
- 공개 자료 분석: 여섯 검사 통과, 이익 감소·IR 인용 유지. 분석 도구 8회.
- 비공개 자료 분석: 여섯 검사 통과, 구조적 정보 제한 확인 후 방향 unknown. 분석 도구 10회.

## 1-3. 검증 실패가 실행 성공으로 표시되던 평가기 수정

잘못된 이익 증가 답을 주입하니 정답 검사는 false지만 평가 함수는 정상 반환했다. 이는 검사 결과와 실행 성공을 혼동하게 하는 평가기 오류였다. 수정 전 실패 테스트 1개를 확인하고, 결과 파일을 보존한 뒤 실패한 검사 이름을 포함해 예외를 발생시키도록 최소 수정했다. 올바른 답의 성공과 틀린 답의 실패 모두 테스트했다. 앞선 통과 보고는 evaluation.json의 개별 체크를 직접 확인한 결과이며, 당시 종료 코드만으로 판단한 것이 아니다.

실제 모델 복구 시험은 `python -m edge_analysis_v2.quality.source_recovery_eval --env-file <환경파일> --artifacts <새 폴더> --case list --model deepseek-flash`로 재현한다. 사전형은 `--case dictionary`다. 실제 API 비용이 들며 제공된 원자료와 읽은 결과만 채점한다. 평가용 계측은 실제 조회 구현을 그대로 호출하고 호출 결과만 기록한다.

이 단계의 검증은 자료 선택·오류 복구·평가기 실패 처리에 한정한다. 단일 실행에서 도구 호출 수가 줄어든 것을 일반적 성능 개선으로 해석하지 않는다. 미등록 질문 발견·성급한 종결의 의미 검토는 아직 별도 개선 대상이다.

최종 확인: 회귀 테스트 469개 통과, 생략 없음. wheel 빌드와 새 복구 코드·재현용 평가 모듈 포함을 확인했다. 실제 모델 시험 네 건의 개별 체크가 모두 참이며 해당 임시 작업 폴더가 정상 종료 후 제거된 것을 확인했다. Git diff 공백 검사도 통과했다. 로컬 수정이며 머지·클라우드 배포는 수행하지 않았다.
