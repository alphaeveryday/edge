# ETF 투표 Redis failover — 이력서 문장과 실측 근거

2026-09-13 기준, **현행 빌드 재실측 반영판**. 원본 데이터: 현행 정본 = `runs/S1-20260913-205812`, `runs/S2-20260913-210503` / 구 계약(불변 1표) 기록 = `runs/S1-20260913-015030·021816`, `runs/S2-20260913-011022·033006`, `runs/S3-20260913-015635·022446`. 상세 기록은 [FAILOVER_RESULTS.md](FAILOVER_RESULTS.md).

## 이력서 문장

> Redis Sentinel failover 실험으로 ETF 투표 집계의 미반영·중복을 실측하고, Lettuce 연결 정책·서킷 브레이커와 멱등 Lua 설계로 장애 격리 및 집계 자동 복구 (장애 구간 SLO 1초 초과 요청 40% → 0%, 무관 API p99 346ms → 2.2ms)

- master kill 시나리오에서 Lettuce disconnectedBehavior·타임아웃 정책별 SLO 초과율·톰캣 스레드 점유·부하 유실을 비교해 즉시 실패 정책 채택 — 스레드 풀 점유 195 → 3, 장애 구간 투표 p99 6,803ms → 7.4ms, 부하 유실 118건 → 0건
- 투표 원본은 DB(unique 제약 + 원자 upsert)에 두고 Redis는 파생 집계로 한정, 장애 구간 Redis 미반영 최대 697건을 재연결 이벤트·주기 기반 DB 재집계로 자동 복구 (실패 로그 ≈ 재조정 delta 검산 일치)
- 사용자별 이전 선택을 비교하는 멱등 Lua(choices 해시)로 재투표·재실행 시 중복 집계 0건 — 커밋 후 캐시 갱신은 @TransactionalEventListener(AFTER_COMMIT)로 순서를 구조적으로 보장, Cluster 전환 대비 전망 단위 해시태그로 동일 슬롯 배치

## 실험 조건 (현행 정본)

- Spring Boot 4.1.0 / Lettuce / MySQL 8.4 / Redis 7, master 1 + replica 2 + Sentinel 3 (Docker Desktop 단일 호스트)
- 현행 계약: 3지선다 BUY/HOLD/SELL, 재투표=마지막 선택 변경(같은 선택 no-op), 전 요청 200
- 현행 구조: 네이티브 upsert(원자 신규/변경) → AFTER_COMMIT 이벤트 리스너가 Redis 갱신 → Resilience4j 서킷(쓰기=repository·읽기=service 폴백, 재조정 replace 는 서킷 밖)
- k6 투표 50rps + 무관 요청(정적 `/`) 50rps, 3분, 부하 60초 후 master SIGKILL
- "실패" 정의: HTTP 상태 실패는 전 시나리오 0(DB-first 설계의 의도) — 클라이언트 SLO(1초) 초과로 정의하고 before / during(주입 후 20초) / after 로 phase 분리

## 주장별 근거

### "SLO 1초 초과 40% → 0%, 무관 API p99 346ms → 2.2ms"

| during 구간 | S1 DEFAULT/5s | S2 REJECT/500ms |
|---|---|---|
| SLO 1초 초과 | **352건 (39.7%)** | **0건 (0%)** |
| 투표 p99 / 최대 | 6,803ms / 9,817ms | 7.4ms / 11.0ms |
| 무관 요청 p99 (평시 ~2.5ms) | 346ms | 2.2ms |
| 스레드 점유 최대 / 부하 유실 | 195 / 118건 | 3 / 0건 |

before / after 구간은 두 시나리오 모두 SLO 초과 0 — 영향이 장애 구간에 국한. S1 은 유실 118건이 이 구간에서 추가로 빠졌으므로 실제 체감은 40%보다 나쁘다.

### 서킷 브레이커 단독 효과 (구 실측과의 차이)

구 계약 빌드(서킷 없음)에서는 S1 SLO 초과 68.1%·무관 p99 972ms였다. 현행 S1 이 39.7%·346ms 로 개선된 것은 DEFAULT 정책에서도 서킷이 열려 후속 호출을 즉시 폴백시키기 때문 — 서킷의 기여를 분리 실측한 셈이다. 그래도 서킷이 열리기 전 블로킹으로 스레드 195·유실 118이 남아, 즉시 실패 정책(REJECT/500ms)과의 병행이 결론이다. 서킷 open 은 실측으로 확인(CallNotPermittedException, S2 계열 1,198건).

### "미반영 최대 697건 자동 복구, 검산 일치"

- S1: Redis 실패 로그 697건 → 재조정이 복구, 최종 DB=Redis 통과
- S2: 실패 로그 639건 ≈ 재조정 delta 640건(±1) — 독립 측정 수렴, 못 세는 케이스 없음
- 복구 경로: DB 원본 → 재연결 이벤트·5분 주기 재조정이 Lua 한 번으로 count·choices 해시 통째 교체. 재투표=변경 계약에서도 스냅샷 교체 방식이라 그대로 수렴
- Sentinel `+switch-master`: 장애 후 5.8~7.3초 (전 런 범위)

### "멱등 Lua·커밋 후 캐시 갱신으로 중복 0"

- 멱등 장치: Lua 가 choices 해시의 이전 선택과 비교 — 같으면 no-op, 다르면 이전 카운터 -1·새 카운터 +1. 같은 요청 재실행(SCRIPT FLUSH 후 EVAL 포함)이 중복 집계로 이어지지 않음은 통합 테스트로 검증(동시 16연타 → 최종 1표 포함)
- 순서 보장: @TransactionalEventListener(AFTER_COMMIT) — 커밋 전 캐시 갱신(롤백 시 유령 표)이 구조적으로 불가능, 커밋 선행은 통합 테스트(별도 커넥션에서 표 가시성 확인)로 검증
- 전 시나리오 DB 중복 레코드 0, 최종 DB=Redis=choices 정합 통과

## 쓰면 안 되는 표현 (실측 없음·낡음)

- "네트워크 차단 시나리오" — S4 미실행 (master SIGKILL 만 실측)
- "비동기 복제로 INCR 유실" — 미반영분은 장애 구간 쓰기 실패분, 복제 유실 실측 없음. "미반영"으로 쓸 것
- "실패 요청 X% → Y%" (HTTP 상태 기준) — 전 시나리오 HTTP 실패 0. SLO 초과율로 표현할 것
- "SAdd 가드"·"재시도 1,070회" — **구 계약(불변 1표·retry) 시절 표현.** 현행 코드는 SADD 없음(해시 이전값 비교)·retry 없음. 구 기록을 인용할 땐 "당시 빌드" 명시
- "68% → 0%" — 서킷 없던 구 빌드 수치. 현행 빌드 근거는 40% → 0% (또는 서킷 효과 분리 서사로 68→40→0)
- "중복 집계 M건 → 0건" — 가드 없는 대조군 미측정
