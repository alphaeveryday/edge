# rules — 콘솔 규칙 엔진 (ALPHA-738)

콘솔 홈을 하드코딩 카드에서 **규칙이 사실 위에서 돌아 나온 결과의 렌더링**으로 교체하는 모듈.
규칙 R01~R19 + 인과 간선 7개 + `evaluate()`가 전부 여기 산다.

이 결과는 `cli.ts`·회귀 테스트와 `pages/ops/*` 화면이 소비한다. 화면은
`pages/ops/consoleFacts.ts`에서 와이어 응답을 검증·변환하고, 배치 사실과 실시간 축을 합쳐
같은 평가 결과를 목록·상세·축 화면에 공급한다.

## 구성

| 파일 | 역할 |
|---|---|
| `types.ts` | Facts(사실)·Violation·Incident·리포트 타입 — **위반 필드 규약**(`target`/`targetId`/`metric`/`unit`/`state`/`why`)이 `RawViolation` 주석에 있다. 정본은 거기다 |
| `rules.ts` | RULES 19종(선언 데이터 + 조건 함수) · EDGES 7개 |
| `evaluate.ts` | 위반 수집 → 인과 병합(사건) → 정렬 · 리뷰 계약 §5 JSON(`buildReport`) · 사건 키 조립(`vidOf`)과 **그 역함수**(`ruleOfVid`) — 소비자가 구분자를 다시 적으면 조용히 아무것도 못 찾는다 |
| `facts-snapshot.json` | 사실 팩(2026-08-03 스냅샷, 목 포함 — mock 플래그로 구분). CLI 기본 입력·회귀 픽스처다. 화면은 `GET /api/v1/console/facts`의 camelCase DTO를 `pages/ops/consoleFacts.ts`에서 검증·변환한다 |
| `cli.ts` | `eval:rules` — UI 없이 §5 JSON 산출 |
| `rules.test.ts` | `test` — 규칙당 위반/비위반 픽스처 + 경계 케이스 (node:test) |

### 돌리는 법 (전제 둘)

⚠️ **`super-admin-ui` 패키지 루트에서** 돈다 — 레포 루트나 이 폴더에서 치면 스크립트도 경로도 못 찾는다.
⚠️ **Node 23.6+ 가 필요하다**(`.ts` 네이티브 실행). 레포에 버전 핀이 없고 배포 워크플로는 Node 20 이다
— PR 게이트(`.github/workflows/ui-test.yml`)는 Node 24 로 돈다.

```bash
cd src && pnpm --filter super-admin-ui test        # 워크스페이스 어디서나 되는 형태
cd src/apps/cloud/super-admin-ui
pnpm test          # node --test 'src/**/*.test.ts'
pnpm eval:rules    # node src/rules/cli.ts [facts.json]
```

Node 직접 실행(cli·test)을 위해 모듈 내부 import 는 `.ts` 확장자를 쓴다(tsconfig `allowImportingTsExtensions`).

⚠️ 이 제약은 **이 폴더 밖에도 적용된다.** `pnpm test` 는 `src/**/*.test.ts` 를 돌리므로, 규칙
결과를 읽는 순수 판단을 화면 쪽에 둘 때도 같은 규약을 지켜야 한다. **JSX 를 쓰는 파일에 그런
판단을 두면 node 가 import 자체를 못 해 변이가 하나도 안 잡힌다** — 판단은 `.ts` 로 내리고
import 에 확장자를 붙인다.

## 명세와 다르게 구현한 지점 (구현 노트)

1. **명세 원문 부재** — `edge-console-rules.md`·`edge-console-datapack-v2.json` 파일이 로컬에 없어,
   레퍼런스 `edgeconsolev4.html`(~/Downloads)의 `RULES`·`EDGES`·`evaluate()`·내장 데이터팩을 추출해 SSOT 로 썼다.
   회귀 기준: 위반 24 · 사건 15 · **P0 6** (스냅샷 회귀 테스트로 고정).
   ⚠️ P0 는 레퍼런스의 5 에서 **6 으로 옮겼다**(ALPHA-738 B2a) — R14 가 비게시 발번을 `seed_note`
   만 보고 P2 로 강등하던 것을 없앴다. 그 값은 합계라 "전량 시드"를 가정할 수 없고, 실 응답에서
   그 수는 "무효화 통지가 안 간 발번"이라 진짜 P0 다. 회귀가 아니라 정정이다.
   ⚠️ 위반·사건은 29·20 에서 **24·15 로 내렸다**(ALPHA-946) — 동봉 스냅샷이 **미완결 당일**의
   캡처인데 산출 다섯에 기준을 싣고 있어 R13 이 다섯 건을 세웠다. 서버가 이제 그 날의 `base` 를
   안 보내므로 픽스처를 계약에 맞췄다. 다섯이 전부 독립 사건이라 사건도 5 준다. 이것도 정정이다.
2. **NOW** — 레퍼런스는 벽시계 상수 고정. 여기서는 `snapshotNow()` = `meta.db`(스냅샷 채취 시각)를
   기본값으로 쓴다. 벽시계로 평가하면 같은 스냅샷의 R02 판정이 시간이 지나며 바뀌어 재현이 깨진다.
3. **evaluated:false 판정** — 명세 §5가 요구하는 "못 돈 규칙 ≠ 조용한 규칙" 구분. 생산자는 **둘**이고
   `RuleResult.notRun` 이 어느 쪽인지 구조로 낸다:
   - `notRun: 'axis'` — `canRun` 이 거짓(읽을 사실 축이 없다). `canRun` 을 가진 규칙 **열하나가
     전부** 대상이다: R03(AWS 상태 전무)·R08(actual 근거 전무)·R10(비교할 점 2개 미만)·R11(구독
     매핑 필드 부재)·R12(큐 축 부재)·R13(기준 있는 산출 전무)·R15(per-ETF 원장 부재)·R16(정책
     필드 전무)·R17~R19(minute 축 부재). 목록을 손으로 적어 세 개(R03·R10·R13)를 빠뜨렸던
     자리다 — 정본은 `RULES` 의 `canRun` 유무이지 이 문장이 아니다.
   - `notRun: 'identity'` — 축은 있었는데 **응답이 사건을 못 가르게** 줬다(사건 식별자 충돌·빈 대상/범위
     축). `canRun` 과 무관하게 `evaluate` 가 그 규칙의 위반을 통째로 버리고 세운다. 계측 공백이 아니라
     계약 위반이라 화면도 다른 칸에 그린다.

   그래서 `canRun` 목록을 "evaluated:false 인 규칙의 전부"로 읽으면 안 된다.
   동봉 스냅샷 기준 실측: **`evaluated:false` 는 R17~R19 셋**이다 — 스냅샷은 배치 원장만 담고
   실시간 세션 축은 화면이 `/sources/minute` 응답을 실어 줄 때만 채워진다. 나머지는 evaluated:true
   이고, 그중 목으로 채워진 것이 `depends_on_mock`(R07·R08·R11·R15·R16 — R12 는 evaluated:true
   지만 목이 아니고, R07 은 canRun 이 없지만 목이다) — **MOCK 배지 수 = 남은 계측 부채**.
4. **§5 예시에 없는 필드** — 전부 "명세가 요구한 성질을 기계 검증할 수 있게" 붙인 것이다.
   - `violations[].absorbed_into` — 흡수된 위반이 리포트에서도 지워지지 않았음을 뿌리 사건 키로 증명.
   - `violations[].vid`·`incidents[].members[].vid` — **사건 키 축**(`${rule}:${targetId}[@scope]`).
     `rule`+`target_id` 만으로는 같은 작업이 두 런에 걸린 날 멤버 두 줄이 글자 하나 안 틀리게 같아져
     조인이 끊긴다.
   - `violations[].scope` — 그 vid 의 시점 범위. 소비자가 `scope ?? run_id` 를 다시 조립하지 않게.
   - `rules[].notRun` — 위 3의 두 종류(`axis`·`identity`).
5. **실행 위치** — 명세는 "서버 쪽이 자연스럽다" 했으나 UI 워크스페이스의 순수 TS 모듈 + node CLI 로 구현했다.
   판정이 클라이언트에 남는 이유는 **실시간 축이 다른 응답에서 오기 때문**이다(사실은
   `/console/facts`, 세션은 `/sources/minute`). §5 JSON 은 CLI 로 UI 없이 나온다.
   ⚠️ 둘을 합쳐도 **19규칙이 다 서지는 않는다** — `/console/facts` 에 AWS 상태·chain·queues·
   ETF 원장·재시도 상한이 없어 R03·R10·R11·R12·R15·R16 은 계속 `evaluated:false` 다. 어댑터 둘을
   만들면 계측이 끝난다고 읽으면 안 된다(남은 것은 아래 **계측 티켓 표**다 — 수를 여기 적으면
   낡는다. 규모의 정본은 `rules.ts` 의 `dep` 집합이고 `rules.test.ts` 가 표와 맞물려 센다).
   **이 선택은 닫혔다** — 엔드포인트가 사실만 주고 평가는 여기 남는다
   ([ADR-0050](../../../../../../docs/adr/0050-console-facts-endpoint.md), 계약은
   [docs/contracts/console-facts-api.md](../../../../../../docs/contracts/console-facts-api.md)).
6. **구 홈 은퇴 — 라우트만 존치** — `/`는 규칙 엔진 사건 목록(`/ops/incidents`)으로 이동하고,
   이전 `OverviewPage`(실데이터 레인 요약)는 `/overview`에 **라우트·컴포넌트로만** 남는다.
   ⚠️ **"남는다"는 메뉴 병존이 아니다** — 사이드바에서 빼는 것이 은퇴의 내용이다(계획 §6-3:
   개요는 자기 질문 "지금 정상인가"에 답할 수 없었다. 답하려면 규칙 P0/P1 과 `sessionHealth` 를
   합쳐야 하는데 합칠 근거가 없고, 나머지 줄은 전부 다른 화면의 더 나쁜 사본이다).
   이 문장을 메뉴 병존으로 읽고 nav 항목을 넣었다가 되돌린 적이 있다(ALPHA-977) —
   `headerRoute.test.ts` 의 `RETIRED_ROUTE_ONLY` 가 그 왕복을 막는다.
7. **`max_retries: 0` = 정책 미선언** — 원장은 재시도 정책이 없음을 `0` 으로 적는다(SFN Retry 블록 0개,
   27개 중 17개). 이를 "상한 0회"로 읽으면 화면이 `1/0` 이라는 없는 분모를 그리고 R16 이 "평가됨"이라
   주장한다. `retryCap()` 에서 한 번만 정규화하고, 상한이 없으면 화면도 "시도 N회 · 상한 미선언"까지만 쓴다.
   레퍼런스 HTML 은 falsy 검사(`t.max_retries &&`)로 우연히 같은 결과를 냈지만 의도가 코드에 없었다.

## ✅ 해소 — R13 의 당일 거짓 P1 (ALPHA-946)

**뿌리는 축이 둘이었다는 것이다.** 기준일 후보는 전부 조회일 미만이라 **적재 창이 지난** 하루의
값인데, 조회일이 KST 오늘이면 `today` 는 **아직 쌓이는 중**이다. 같은 축이 아닌 둘을 나눠 ±25% 에
걸었다. dev 배포본 실측(2026-08-11 14:27 KST)에서 다섯 중 **넷**이 그래서 거짓 P1 이었다
(`o.trig` −100% · `o.pub` −71% · `o.asr` −29% · `o.evt` −59%).

**고침은 서버 한 술어다** — 조회일이 KST 오늘이면 산출 다섯 전부의 `base` 를 안 보낸다
(`JdbcConsoleFactsRepository.outputs`). **이 층은 판정 코드 0줄**: `hasBase` 가 이미 기준 부재를
"판정 대상 아님"으로 적고, 다섯이 다 빠지면 `canRun` 이 거짓이라 R13 이 **못 돎**으로 선다.
없는 사실을 지어내지 않고 기존 "기준 없음" 규약을 탄다.

⚠️ **`dep` 문장에 갈래를 하나 더했다** — 당일 조회가 이제 늘 그 문장을 띄우므로, 사유를
"표본이 없다"로만 두면 **원장에 있는 표본을 찾아 나서게** 된다. 어느 하나를 지목하지는 않는다
(와이어는 `base: null` 하나로 오고, **가르려고 이 층에서 날짜를 다시 재면 판정 주체가 둘이 된다**).

⚠️ **"완결"이 아니라 "적재 창이 지났다"이다.** 이 술어는 완결을 증명하지 않는다 — 아래 잔여 1.

### 왜 세 라운드가 틀렸나 — 후보와 반례

| ❌ 후보 | 반례 |
|---|---|
| `runs[].deadline` | hard deadline 이라 슬롯보다 한참 뒤다 — 스냅샷의 `etf-daily:…T15:40` 슬롯 deadline 은 **21:40** |
| "그 레인의 런이 귀결되면 완결" | 뉴스 갈래 셋은 `available_at` 하루 누계라 런이 끝나도 행이 는다 |
| ~~"`o.trig` 은 1분 레인이 함께 써서 런 귀결로 못 잰다"~~ | **이 반례 자체가 거짓이었다** — 1분 레인은 `minute_price_trigger` 라는 **다른 표**에 쓴다(`minute/price_consumer.py`, ALPHA-709 "트리거 축은 둘이다") |
| 실시간 세션 `phase == 'FINALIZED'`(15:30) | **실측 반증** — 다섯 중 넷이 15:30 이후에도 자란다 |

**답을 준 것은 추측이 아니라 측정이다.** 적재 창이 산출마다 다르다:

| 산출 | 그 날 값이 쌓이는 창 |
|---|---|
| `o.trig` | **시장 SFN 한 번**(기본 `cron(40 15 ? * MON-FRI *)`)이 통째로 넣는 계단 함수. ⚠️ 행의 `detected_at`=15:30 은 `load_price_triggers.py` 의 **멱등 키**이지 적재 시각이 아니다 |
| `o.doc`·`o.asr`·`o.evt` | **하루 종일** — `available_at` 이 곧 날짜 버킷이고 1분 레인과 배치가 함께 먹인다 |
| `o.pub` | **날짜 경계를 넘는다** — `trade_date` 가 적재와 분리돼 있고 writer 가 상주 소비자다 |

다섯 전부에 참인 술어는 **"그 날이 다 지났는가"** 하나뿐이라 산출별로 가르지 않았다.

🔴 **남은 잔여 셋**(이 조각 범위 밖 — 정본은 계약 문서 「미완결일」 절):

1. **지난 날의 버킷은 양방향으로 흔들린다.** `document.available_at` 의 뜻도 충돌 처리도 writer
   마다 다르다 — 배치 둘(`assemble_events.py`=**`published_at`** / `load_documents.py`=`fetched_at`
   폴백 `published_at`)은 `ON CONFLICT DO NOTHING` 이라 과거 버킷을 **늘리고**, 1분 레인
   (`canonical_news.py`=처리 시각)은 `DO UPDATE … GREATEST` 라 정정이 오면 값을 앞으로 밀어
   과거 버킷을 **줄인다**. ⚠️ 버킷을 정하는 것은 writer 가 아니라 그 행의 `available_at` 이
   어느 날짜인가다. 뉴스 day-close 는 00:10 에 돌며 **어제 창**을 처리한다. `o.pub` 도 같은
   부류다 — 실측(행 기준) **08-03 은 절반이 익일 적재**. 정본은 계약 문서 「미완결일」 절.
2. **`o.trig` 은 시장 SFN 이 끝난 뒤엔 과잉 억제** — 자정까지는 사실상 확정인데 판정을 안 한다.
3. 🔴 **그 날의 진짜 결손이 자정까지 조용해진다** — 산출이 통째로 0 인 장애를 R13 이 당일에 잡던
   경로가 사라지는데 대신 잡을 규칙이 없다(완전성 축이 대부분 `UNKNOWN`, ALPHA-728).


## 🔴 알려진 결함 — 죽은 인과 경로 둘

리뷰 라운드에서 **간선 일곱 중 하나와 승격 로직 하나가 구조적으로 도달 불가**임이 드러났다.
픽스처로는 못 보여주므로 구조 단언으로 못 박아 뒀다(`rules.test.ts`) — 도달 가능해지는 순간
그 테스트가 깨지고, 그때 진짜 사례 테스트를 더하면 된다.

| 죽은 것 | 왜 |
