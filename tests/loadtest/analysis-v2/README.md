# 분석 v2 실행 자동화 — 측정 기록

v2 전망·가격변동 실행 자동화의 기준 측정과 계약 재현 기록이다(ALPHA-1142, 동시 실행은 ALPHA-1157). 기준 측정, 로컬 검증, dev 검증, 실제 스케줄 관측을 구분해 적는다.

## 구성과 재현

- `aws/`: dev 조회 SQL(`q1.sql`~`q4.sql`)과 조회 스크립트(`dbq.sh`).
- `local/`: 탐침 `probe.py`, 격리 DB `docker-compose.yml`. 탐침은 결과를 `local/results.jsonl`에 쓴다. 실행 구조 대안 비교는 `review_probe.py`(아래 '실행 구조 대안 검토').
- `dev/`: 배치 실행·조회 스크립트 `batch_run.py`. 결과를 `dev/results/`에 쓴다. `report <실행 이름>`은 끝난 실행을, `latest`는 가장 최근 실행(스케줄 발화 포함)을 집계한다.
- 측정 원본(실행·조회 결과 JSON, 탐침 결과 JSONL)은 저장소에 두지 않는다. 위 결과 경로는 `.gitignore`에 있다. 이 문서 수치의 근거인 2026-10-02 원본 28개는 커밋 `66123f75`의 같은 폴더에 남아 있고 `git show 66123f75:tests/loadtest/analysis-v2/<경로>`로 꺼낸다. 아래에서 인용하는 원본 파일 이름은 그 커밋 기준이다.
- 측정 시점 코드: `4311a19b`. 배포 이미지 `analysis-v2-cb9fa258`(작업 정의 9번)과 v2 소스 차이 0줄. 대상 목록 37종, 해시 `dc2373347520956f073a75214de38db1a8af9ebcd22a452efe73480f30f9225c`.

## 기준 측정 (2026-10-02)

**연결 상태** (코드 관찰과 AWS dev 조회)

- v2 호출자는 없다. 스케줄러와 Airflow DAG 어디에도 v2 호출이 없고, app-api는 호출 권한만 있고 코드가 없다. v2 실행 이력은 수동 3건이 전부다.
- v2 결과 소비자도 없다. tenant-sync-api와 super-admin은 v1 표(`explanation_*`, `tenant_delivery`)만 읽는다. v2 결과는 v2 조회 API로만 나간다.
- v1 가격변동 경로는 가동 중이다. price-consumer → outbox → relay → SQS `price-explanation-realtime` → analysis-consumer(자동 확장 0~4) → `explanation_result` → `tenant_delivery`. 10월 1일에도 소비자가 처리했다.
- v1에는 전망 생산자가 없다. v1 장마감 analyze 단계는 SFN에서 제거된 상태다. 전망은 v2 신규 기능이며 대체할 v1이 없다.
- 트리거의 `entity_id`가 ETF 6자리 코드다. v2가 `minute_price_trigger`를 같은 값으로 조회한다.

**실측** (dev, 표본이 작으므로 분포 추정에 쓰지 않는다)

- 클라우드 실행 3건(전망 1, 가격변동 2, 모두 091160, 성공): SFN 전체 257초, 170초, 121초. 구간은 ECS 기동 21~28초, 컨테이너 시작 2초, 원천 읽기와 시작 처리 1초 이하(전망 1건), LLM과 도구 56~204초, 저장과 관측 내보내기 1초 이하, ECS 종료 25~27초. 도구 실행 합계는 0.1~0.8초다.
- DB 이력의 실데이터 분석(첫 도구 시작부터 발행까지, 로컬 실행 포함): 전망 완료 11건 135~226초, 중앙값 161초, 실패 2건. 가격변동 완료 13건 56~112초, 중앙값 79초, 실패 0건. 대상 ETF 10종.
- 전망 실패 2건은 모델이 낸 근거 ID 검증 실패 1건과 SDK 최종 응답 실패 1건이다.
- 클라우드 1건 실행 중 `DatabaseConnections`는 20에서 23으로 3 늘었다(2건 관측). `FreeableMemory` 변화는 6MB 이내다.
- RDS 7일: 연결 20~32, `FreeableMemory` 578~651MB, `max_connections` 181. 인스턴스는 db.t4g.small이다.
- 역할 연결 한도(pg_roles 조회): writer 5, reader 3, api_reader 5.
- 가격변동 트리거 큐 발행량(회수 포함, 8거래일): 하루 5~47건, 5분 최대 25건(9월 22일 09:00). 가장 오래 대기한 메시지는 하루 최대 13분~2.1시간.
- 뉴스 배치는 00:10(00:20~00:22 종료)과 08:10에 돈다. 08:10 배치는 08:00까지 저장하는 전망에 들어갈 수 없다. 이 관찰은 뉴스 배치 스케줄에 한정되며 다른 입력의 최신성을 말하지 않는다.

**로컬 실험** (PG 16.14 컨테이너 2GB, 실제 마이그레이션 77개, 실제 `worker.run`과 저장 코드. LLM, 원천 조회, S3는 대역)

- 배포된 한도(writer 5, reader 3)에서 동시 1건은 성공한다. 동시 2건은 13회 중 11회가 1건만 성공, 2회가 0건 성공이며 2건 모두 성공한 경우는 없다. 동시 4건과 8건에서는 0~1건만 성공한다. 오류는 `too many connections for role`이다.
- 한도를 로컬에서만 풀면 동시 37건이 모두 성공한다(writer 세션 111개, 컨테이너 메모리 약 120MiB → 341MiB). 전망 37건과 가격변동 37건을 함께 돌리면 `max_connections` 181에 걸려 74건 중 18건이 실패한다.
- 재시도 계약: 실패한 시도는 원인과 무관하게 분석 ID를 소진한다. 워커가 시작하자마자 관측 manifest를 `IfNoneMatch`로 선점하기 때문이다. 완료 ID를 워커로 다시 실행해도 같은 이유로 실패한다. 저장 결과 재사용은 API 계층에만 있다.
- 강제 종료된 실행은 `running` 행을 남기고 락은 풀린다. 새 ID 재시도는 성공한다.
- 연결 한도나 ETF 락으로 진 실행은 DB 행을 남기지 않는다. 실패 사유는 SFN 실패와 S3 manifest에만 남는다.
- 같은 ETF의 전망과 가격변동 병행은 ETF 락이 아니라 writer 한도 때문에 한쪽이 실패한다. 한도를 풀면 둘 다 성공한다.

**기각하거나 정정한 가설**

- '커넥션 풀 대기로 느리다': 기각. v2에는 풀이 없고 `psycopg.connect` 직접 연결이다. 연결 생성은 로컬 최대 76ms다.
- '연결을 오래 쥐어 메모리가 고갈된다': 현재 요구 범위에서는 근거 없음. 건당 writer 3개를 LLM 대기 내내 쥐는 것은 사실이나, 지금 동시 실행을 막는 것은 메모리가 아니라 역할 한도 5다.
- '건당 약 20분': 실측과 맞지 않는다. 건당 2~4분이다. 10월 1일 로컬에서 10종 전망을 2개씩 돌린 묶음이 약 19분 걸렸는데, 이 수치의 출처일 수 있다(추정).
- '1,100초 제한과 충돌': 충돌하지 않는다. 실제 상한은 모델 대화 제한 300초(`run_model` 기본값)다. 관측 최대 226초는 첫 도구 시작부터 발행까지라 구간이 달라서 여유를 초 단위로 단정하지 않는다. 긴 꼬리 실패 위험은 남는다.
- 'dev 문서의 최대 2개': 로컬 대시보드 경로(건당 writer 2개) 기준이다. 클라우드 워커 경로는 건당 3개라 2개 동시 실행이 성립하지 않는다.

**미확인**

- DeepSeek 동시 호출 한도(실측은 동시 2까지).
- 실제 RDS에서 writer 세션이 늘 때의 메모리 변화(로컬 수치는 참고용).
- 37종 전체의 건당 시간 분포(표본은 10종).
- 가격변동 `analysis_at`의 의도된 기준(트리거 생성 시각으로 보이나 작성자 확인 전).
- Step Functions 내장 기능의 실제 동작 네 가지(아래 계획에 표시).

## 전망 배치 (ALPHA-1142, 동시 실행은 ALPHA-1157)

EventBridge Scheduler → 배치 워크플로(`edge-dev-analysis-v2-outlook-batch`) → Inline Map → 기존 단건 워크플로(`edge-dev-analysis-v2`) 중첩 호출. 정의는 `infra/terraform/modules/analysis-v2/outlook_batch.asl.json`, 자원은 같은 폴더의 `outlook_batch.tf`다. 분석 로직, 요청 계약, 기준시각과 결측 규칙은 바꾸지 않았다.

### 실행 계약

- **업무 기준시각**: 스케줄의 예정 시각이 `analysis_at`이 된다. 실제 시작이 늦어지거나 스케줄러가 재전달해도 같은 값이다. 수동 재실행은 같은 문자열을 입력으로 준다. 소수 초 없이 `Z`로 끝나는 UTC 표기(`2026-10-01T18:00:00Z`)만 받는다. 분석 ID가 이 문자열에서 나오므로 같은 순간의 다른 표기는 다른 작업이 된다.
- **분석 ID**: `MD5(outlook:ETF:analysis_at:시도 번호)`. 시도마다 새 ID이고, 같은 작업의 같은 시도는 어느 배치에서 계산해도 같은 ID다. 논리적 작업은 종류, ETF, 기준시각이다.
- **완료분 재사용**: 시도 0부터 해당 ID의 저장 상태를 조회 API(`GET /v2/analyses/outlook/{id}`)로 읽는다. 완료면 재사용, 실패면 다음 시도, 없으면 실행한다. '없음'은 앱이 낸 404(`Analysis not found`)만이다. API Gateway가 낸 404나 읽을 수 없는 응답은 `unknown`으로 두고 분석을 시작하지 않는다. 날짜별 최신 발행본은 보지 않으므로 같은 날 다른 기준시각의 작업을 건너뛰지 않는다.
- **재시도**: 항목당 시도 2회(재시도 1회). 소진되면 그 항목은 실패다. `max_attempts`를 올려 재실행하면 실패 항목의 다음 시도만 돈다.
- **저장 뒤 실패**: 단건 워크플로가 실패로 끝나도 같은 ID의 저장 상태를 다시 읽어 판정한다. 종료 코드보다 DB가 정본이다.
- **동시 수**: 분석은 슬롯 수(`analysis_slots`, dev 3)만큼 동시에 돈다. 상한은 단건 워크플로의 자리 확보가 지고, 워커의 분석 슬롯이 한 번 더 확인한다. 아래 '동시 실행과 분석 슬롯' 참고.
- **시작 전 확인**: 단건 워크플로의 실행 중 개수가 슬롯 수 이상이면 30초 간격으로 기다린다. 자리를 기다리기만 할 실행을 미리 시작하지 않기 위한 것이고 상한은 아니다. 자리를 기다리는 단건 실행도 실행 중으로 센다. 같은 작업을 다른 배치가 이미 돌리고 있으면 끝나기를 기다렸다가 그 결과를 쓴다.
- **마감**: 기준시각과 같은 UTC 날짜의 23:00Z(= 08:00 KST)를 절대 시각으로 계산한다. 마감이 지나면 새 분석을 시작하지 않는다. 마감 뒤에 발행된 결과는 완료가 아니라 `late`로 센다. 정의의 `TimeoutSeconds`(8시간)는 마감 장치가 아니라 안전망이다.
- **결과와 알람**: 전 항목이 마감 전 완료일 때만 성공한다. 그 밖에는 `OutlookBatch.Incomplete` 또는 `OutlookBatch.DeadlineExceeded`로 실패하고 cause에 건수와 미완료 항목이 실린다. 실패와 시간 초과 알람, 스케줄 전달 실패 DLQ 알람이 기존 알람 토픽으로 간다.

### 동시 실행과 분석 슬롯 (ALPHA-1157)

- **두 겹의 상한**: 같은 `analysis_slots` 값을 두 곳에서 지킨다.
  1. 단건 워크플로의 자리 확보(ALPHA-1161, 2026-10-02 23:23 KST 배포): Fargate를 띄우기 전에 실행 제어 Lambda가 `analysis_execution_slots` 표에 자리를 기록한다. 자리가 없거나 같은 종류·ETF가 이미 돌고 있으면 워크플로가 30초 간격으로 기다린다. 기다리는 동안 태스크도 DB 연결도 쓰지 않는다. 동작과 복구는 `src/apps/cloud/analysis-engine-v2/docs/price-automation.md`에 있다.
  2. 워커의 분석 슬롯(ALPHA-1157): 아래 '슬롯'. 1번이 생긴 뒤로는 평소 기다릴 일이 없는 두 번째 확인이다(37종 실측 38건 모두 대기 0초). ALPHA-1167 뒤로는 워커가 실행 ARN을 받지 못한 경우에만 쓴다.
- **슬롯**: 클라우드 워커는 ETF 락을 잡은 뒤, 원천을 읽기 전에 슬롯 하나를 잡는다(`cloud/worker.py`의 `acquire_slot`). 슬롯 수의 기본값은 1이고 dev는 3이다. 연결 한도 마이그레이션과 새 워커 이미지가 dev에 배포된 것을 확인한 뒤 별도 변경으로 올렸다(머지마다 마이그레이션, 이미지, terraform이 순서 없이 따로 적용된다). 없으면 5초 간격으로 최대 10분 기다린다. 슬롯은 워커가 분석 내내 쥐는 락 연결의 세션 advisory lock이라, 태스크가 죽으면 연결과 함께 풀린다.
- **적용 범위**: 단건 워크플로가 자리를 확보하고 슬롯 수(`ANALYSIS_SLOTS`)를 워커에 넘긴다. 배치, 조회 API의 분석 요청, 수동 시작, 가격변동 접수가 모두 이 워크플로를 지나므로 같은 상한을 받는다. **로컬 대시보드 실행은 슬롯을 잡지 않는다.** 클라우드 워커를 거치지 않기 때문이고, 이 경로는 통제하지 못한다.
- **락과 감사 기록(ALPHA-1167)**: 단건 워크플로가 워커에 실행 ARN(`ANALYSIS_EXECUTION_ARN`)을 넘기면, 클라우드 워커는 ETF 락·워커 슬롯·분석 ID 락을 잡지 않고 DB 단계마다 연결을 열고 닫는다. 같은 종류·ETF 하나씩과 상한은 자리 표가, 같은 분석 ID 한 번은 실행 이름과 관측 manifest 선점이 맡는다. 새 결과는 발행 트랜잭션이 자기 자리 행을 `FOR SHARE`로 잠근 채 커밋하고, 자리가 이미 회수됐으면 발행하지 않는다. 툴 기록의 독립 커밋과 발행 트랜잭션 경계는 그대로다. 실행 ARN이 없으면(워크플로 정의가 워커 이미지보다 오래된 동안) 이전처럼 락 3개와 연결 3개를 쓴다. 로컬 대시보드도 이전과 같다.
- **연결 수명**: 실행 ARN이 있는 클라우드 분석 1건의 연결이다. 모델을 기다리는 동안 writer 연결은 0개다. 단건 워크플로에서 자리를 기다리는 실행은 태스크를 띄우지 않고, 30초마다 실행 제어 Lambda가 writer 연결을 잠깐 연다(Lambda 예약 동시 실행 3이라 많아야 3개).

  | 연결 | 열림 | 닫힘 | 쥐는 것 |
  |---|---|---|---|
  | 원천 연결(reader) | 원천 읽기 | 원천 읽기 직후(초 단위) | |
  | 단계 연결(writer) | 단계마다: 시작 행, 이전 설명과 툴 정의 등록(한 번), 툴 기록마다, 초안 근거 검증, 발행, 근거 표 읽기, 전달 등록, 관측 내보내기 | 그 단계 끝 | 발행 때만 자기 자리 행(`FOR SHARE`) |
  | 실행 제어 Lambda(writer) | 호출마다 | 호출 끝 | 자리 확보와 반납 |

  실행 ARN이 없는 경로는 락 연결(ETF 락·슬롯), 작업 연결(분석 ID 락·결과 저장), 감사 연결을 분석 내내 쥔다.
- **연결 재시도**: 연결이 거절되거나 서버가 세션을 끊으면(연결 실패, SQLSTATE 08·57P01~57P03·53300) 그 단계 전체를 0.5초부터 두 배씩(실제 대기는 그 절반~전부 사이 무작위), 합 20초 안에서 다시 한다. 단계는 멱등이다: 시작 행·정의 등록은 충돌 시 비교, 발행은 완료 상태면 저장된 결과를 돌려주고, 툴 기록은 같은 값이면 저장된 결과를, 다르면 유일 키 위반을 낸다. 문장 시간 초과(57014), 제약·데이터 오류, 입력 오류는 다시 하지 않는다. 모델은 다시 부르지 않는다.

- **역할 연결 한도**: writer 5 → 20, reader 3 → 6(`V202610022100`).

| 구성 | writer | reader |
|---|---|---|
| 실행 중 3건 | 9 (건당 3) | 3 (원천 읽기는 슬롯을 잡은 뒤에만) |
| 워커에서 슬롯을 기다리는 태스크 | 6 (건당 1, 락 연결만) | 0 |
| 로컬 대시보드 실행 2건(슬롯 밖) | 4 (건당 2) | 2 |
| 여유 | 1 | 1 |
| 합계 | 20 | 6 |

  2026-10-02 dev 조회: 전체 세션 29, 최근 7일 최대 35, `max_connections` 181. `edge` 21, `airflow_meta` 4(한도 10), `app_sync_ro` 1, v2 역할 0(`aws/dbq-roles-20261002.json`).

  동시 3건 실측(아래 '37종 전체 실측 — 동시 3건')에서 writer는 최대 9, reader는 최대 3, 전체 세션은 최대 39였다. 단건 워크플로가 자리를 먼저 확보하므로 '워커에서 슬롯을 기다리는 태스크' 몫 6은 쓰이지 않았다. 한도는 그대로 둔다. 실행 제어 Lambda와 분석을 마친 태스크의 내보내기 연결이 이 몫에서 나간다.
- **툴 정의 동시 등록**: 동시에 시작한 분석이 같은 툴 정의를 처음 등록하면 한쪽이 `(function_name, version)` 유일 키에 걸려 실패했다(로컬 재현). 등록의 충돌 처리를 모든 유일 키로 넓혔다. 다른 정의를 거절하는 비교는 그대로다.

### 알려진 한계

- 자리 대기는 공정하지 않다. 기다리는 단건 워크플로는 30초마다 다시 확인할 뿐 줄을 서지 않는다. 배치는 실행 중 개수가 슬롯 수 이상이면 새로 시작하지 않으므로, 기다리는 다른 실행에 자리가 돌아간다.
- 단건 워크플로의 자리 대기에는 시간 제한이 없다(워크플로 전체 제한 8시간). 배치가 단건을 기다리는 제한은 1,500초라서, 배치가 시작한 단건이 다른 실행에 밀려 오래 기다리면 배치 쪽 대기가 먼저 끝난다. 그때 단건이 중단되면 배치는 그 시도를 실패로 세고 다음 시도로 넘어간다. 중단되는지는 확인하지 못했다. 배치는 실행 중 개수를 보고 시작하므로 확인과 시작 사이에 다른 실행이 끼어들고 그 뒤로 자리가 20분 가까이 안 날 때만 생긴다. 관측한 적은 없다.
- 실행 제어 Lambda는 예약 동시 실행 3이다(ALPHA-1166 전에는 1). 호출이 스로틀되거나 Lambda 서비스 오류가 나면 워크플로가 전용 규칙으로 8회까지 지터를 두고 재시도한다(간격 2초부터 두 배, 최대 20초). 함수 자체의 오류는 따로 3회 재시도한다(5초, 10초, 20초). 동시 실행 1이던 37종 실측에서 38건 중 2건이 스로틀됐고 모두 재시도로 넘어갔다. 수동 4건 동시 시작에서는 한 건이 3회를 다 썼다. 자리 확보에서 재시도를 다 쓰면 그 단건 실행은 분석 없이 실패하고 배치는 시도 하나를 잃는다. 분석이 끝난 뒤 자리 반납에서 다 쓰면 단건 실행은 실패로 끝나지만, 배치는 저장 상태를 다시 읽어 완료로 판정한다. 반납하지 못한 자리는 다음 자리 확보가 회수하는데, 근거는 실행 이력의 `STOPPED`, ECS의 `STOPPED`, RunTask를 부르지 않은 실행뿐이다. 확인하지 못한 자리는 점유로 남아 상한과 같은 종류·ETF 제약에 들어가고, 수동 복구를 기다린다(`src/apps/cloud/analysis-engine-v2/docs/price-automation.md`). ALPHA-1166 전에는 이런 자리의 태스크를 ECS가 `MISSING`으로 답하면 다른 ETF의 자리 확보까지 실패했다(아래 '실행 구조 대안 검토'의 C1).
- (실행 ARN이 없는 경로) 워커의 슬롯 대기(두 번째 확인)는 10분 안에 슬롯이 안 나면 `SlotUnavailable`로 실패한다. 원천과 모델은 시작하지 않는다. 이 대기 중인 태스크는 writer 연결 1개를 쥔다.
- 로컬 대시보드 실행은 두 상한 모두의 밖이다. 역할 한도에 2건 몫(writer 4, reader 2)을 잡아 두었을 뿐이다.
- 보유종목 비중 합이 1을 넘는 ETF는 워커가 분석을 시작하기 전에 거부한다(ALPHA-1162, 분석 입력 검증). 그 스냅샷이 최신인 동안 몇 번을 시도해도 실패하므로 그날 37종 전체 저장은 성립하지 않는다. 2026-08-01 이후 26개 거래일 중 25일에 37종 가운데 1종 이상이 해당한다.
- (실행 ARN이 없는 경로) 분석을 마친 태스크는 연결 3개를 놓고 관측 내보내기용 1개를 잠깐 연다. 이 연결은 위 표의 '기다리는 태스크' 몫에서 나간다.
- 자리를 잃은 옛 워커는 새 결과를 발행하지 못하지만, 모델 호출과 툴 기록은 끝날 때까지 계속할 수 있다(비용). 툴 기록은 그 분석 ID에만 묶여 다른 분석의 근거가 되지 않는다.
- 연결 재시도의 합이 20초를 넘는 장애는 그 시도를 실패시킨다. 그때 DB가 실패 기록도 받지 않으면 행이 `running`으로 남을 수 있다(원래 오류는 그대로 올린다).
- (실행 ARN이 없는 경로) 태스크의 호스트가 연결을 닫지 못하고 사라지면, DB가 끊긴 것을 알아챌 때까지 그 슬롯이 잡혀 있다. 프로세스 종료나 태스크 중지는 연결이 닫혀 바로 풀린다.
- 슬롯 수는 Terraform과 실행 제어 Lambda가 3 이하로 제한한다. 연결 한도 20이 3건 기준이라서다. 4건 이상은 재지 않았다.
- 진행 중인 분석은 마감이 지나도 중단하지 않는다. 끝난 뒤 `late`로 드러난다.
- 강제 종료된 시도의 `running` 행은 그대로 남는다(조회 API는 실패로 판정한다).
- 공휴일에도 평일 스케줄대로 돈다.
- 기준시각은 스케줄 예정 시각과 같다. 기준시각을 시작 시각보다 앞당기려면 입력을 계산하는 단계가 따로 필요하다.
- 스케줄은 당일 00:00~08:00 KST 사이여야 한다. 전망의 날짜는 기준시각의 한국 날짜이고, 마감은 기준시각과 같은 UTC 날짜의 23:00Z로 계산하기 때문이다.
- 수동 실행 문서의 전망 기준시각 관례(해당 날짜 08:30 KST)와 다르다. 08:00 마감 전에 도는 배치에서는 08:30이 미래 시각이 되고, v2 API의 분석 요청은 미래 기준시각을 거절한다(워커를 직접 부르는 경로에는 이 검사가 없다).

**대안 B는 조건을 갖추면 채택할 수 있다.** B는 단건 워크플로의 자리 표(`analysis_execution_slots`)를 실행 소유권으로 그대로 쓰고, 워커는 DB 연결을 연산마다 열고 닫는 안이다. 시간 만료 lease와 heartbeat는 새로 만들지 않는다. 조건은 넷이다.

1. 클라우드 실행은 모두 자리 표를 거친다. IaC에서 워커 태스크를 시작할 권한은 단건 워크플로 역할에만 있다(`modules/analysis-v2/main.tf`의 `ecs:RunTask`). 수동 RunTask와 로컬 대시보드는 밖이다.
2. 태스크를 확인하지 못한 채 자리를 회수하는 틈을 막는다. 지금 회수 판정(`cloud/control.py`의 `tasks_stopped`)은 실행 이력에 태스크 제출 기록이 없으면 ECS를 묻지 않고 회수한다(실험 C2). RunTask 호출 도중 실행이 중단되면 태스크가 떠 있어도 기록이 없을 수 있다. 지금은 워커의 ETF 락이 이때 둘째 실행을 거절하지만 B는 그 락을 없앤다. 그래서 B에는 발행 저장 트랜잭션에서 자기 자리 행이 아직 있는지 확인하는 보완이 필요하다(아래 '구현 전에 해결할 것' 2).
3. 한 시도 안의 재시도는 연결 계열 오류에만, 트랜잭션 단위로, 시간 상한을 두고 한다. 툴 기록 저장은 유일 키 위반 때 되읽어 같은지 비교한다(실험 S, R).
4. 연결 생성 비용을 줄인다. 비밀값과 boto3 클라이언트를 프로세스 안에 캐시하고 툴 정의 등록과 관측 내보내기를 한 연결로 묶는다. 이 환경의 새 연결 1회는 수 밀리초가 아니다(아래 '연결 비용과 풀').

이 밖에 B와 무관하게 **지금 배포에 있는 결함 하나**를 찾았다(실험 C1). 반납 없이 끝난 실행의 자리가 남아 있는 동안 ECS가 그 태스크를 `MISSING`으로 답하게 되면, 그 뒤 모든 종류·ETF의 자리 확보가 실패한다. 회수 판정이 `MISSING`을 '종료 확인 불가'로 보고 예외를 내기 때문이다. 멈춘 지 13시간 지난 태스크가 `MISSING`인 것은 확인했고, 몇 시간부터 그렇게 되는지는 재지 않았다. 10-03 dev 조회로는 지금 남은 자리가 없다고 판단한다(아래 C1). 확인 범위는 그 절에 적었다.

지금 바로 B가 필요한 것은 아니다. 현재 구조로 dev에서 37종을 81분 32초에 저장했다(동시 3건). B를 구현하더라도 먼저 동시 3건을 유지한 채 연결 수명만 바꿔 검증하고, 동시 수 상향은 별도 단계로 잰다. 두 변경의 효과를 섞지 않기 위해서다.

### 연결 3개의 목적

| 연결 | 세션 락 | 그 밖의 쓰임 | 클라우드에서 같은 보장을 주는 것 |
|---|---|---|---|
| 락 연결 | ETF 락 `cloud:{종류}:{ETF}`, 워커 슬롯 `cloud:slot:{i}` | 거시·재무 입력 읽기, 가격변동 전달 등록 | 자리 표의 `request_key` 유일 키와 자리 수 |
| 작업 연결 | 분석 ID 락 | 시작 행, 이전 설명 읽기, 초안 근거 검증, 발행 저장, 실패 기록 | 실행 이름 = 분석 ID, 관측 manifest 선점(`IfNoneMatch`) |
| 감사 연결 | 없음 | 툴 기록 저장 | 락이 없어 연결을 짧게 써도 계약이 그대로다 |

- 세션 락 셋은 연결 둘에 있다. 감사 연결이 따로인 것은 락이 아니라 저장 분리 때문이다. `ToolStore`는 발행 트랜잭션과 섞이지 않는 전용 연결을 요구한다(`_require_idle`). 툴 호출은 분석 안에서 한 번에 하나다(`agent/runner.py`의 `gate`).
- 발행 때 잡는 ETF별 락(`pg_advisory_xact_lock`)은 트랜잭션 락이라 B에서도 그대로다.

| 성질 | 보장 | 근거 |

| 전체 동시 수 상한 | 한다 | 트랜잭션 락(`analysis-v2-capacity`) 안에서 센다, 실험 C5 |

순서가 뒤집힌 가격변동은 이렇게 된다(실험 O1). 같은 ETF의 t1(10:00) 사건이 t2(10:10) 뒤에 실행되면 t1은 완료되고 자기 행도 게시되지만, t2가 이미 전달돼 있어 금융사로 전달되지 않는다(`enqueue_movement`의 `analysis_at` 비교). 최신 조회는 더 새 것을 고르고, 뒤 사건 t3의 이전 설명 사슬에도 t1은 들어가지 않는다. 덮어쓰기는 없지만 t1의 정보는 빠진다. 늦은 사건을 합칠지, 버릴지, 따로 전달할지는 정해지지 않은 제품 정책으로 남긴다.

### 실험

`local/review_probe.py`. probe.py와 같은 컨테이너(PG 16, 2 GiB, `max_connections` 181), 마이그레이션 87개, 실제 `worker.run`, `execute_request`, 저장 코드, 실행 제어 함수 `control`을 쓴다. 모델, 원천 조회, S3, SFN·ECS 응답은 대역이다. ### 재시도

재시도 단위를 셋으로 나눈다. 연결 생성 재시도는 아무 연산 앞에서나 안전하다. 문장 하나 재시도는 트랜잭션 안에서는 쓰지 않는다(오류가 난 트랜잭션은 이미 되돌려진다). 트랜잭션 전체 재시도는 그 트랜잭션이 멱등일 때만 쓴다.

| 연산 | 다시 불러도 되는가 | 근거 |
|---|---|---|
| 시작 행 `begin` | 된다 | `ON CONFLICT DO NOTHING` 뒤 같은 입력인지 비교 |
| 툴 정의 등록 | 된다 | 같은 방식(#1088) |
| 툴 기록 `save_run` | 지금은 안 된다 | 유일 키 위반(실험 R). 되읽어 비교하도록 바꾸면 된다 |
| 발행 저장 `save_*` | 된다 | 완료 상태면 쓰지 않고 저장된 결과를 돌려준다(실험 R, F3, F4) |
| 실패 기록 `fail` | 된다 | `status='running'`인 행만 바꾼다 |
| 가격변동 전달 등록 | 된다 | 같은 분석이 이미 전달됐으면 0건(`enqueue_movement`) |

- 재시도할 오류: 연결 실패와 서버 쪽 세션 종료(SQLSTATE 08 계열, 57P01~57P03), 역할 연결 한도 초과(53300). 그 밖의 오류(`ValueError`, `ToolInputError`, 유일 키·검사 제약 위반, 데이터 오류)는 재시도하지 않는다. 문장 시간 초과(57014)는 재시도로 해결된다는 근거가 없어 넣지 않는다.
- 시간 상한: 연산마다 수십 초 이하로 두고, 분석 태스크 제한(1,100초)과 전망 마감(08:00)을 넘지 않는다. 같은 시도 안의 재시도라 모델은 다시 부르지 않는다.

| 실패 | 지금 | 권고 |
|---|---|---|
| 연결·트랜잭션의 일시 오류 | 그 시도가 실패하고 모델 비용을 다시 쓴다 | B에서 위 범위의 재시도 |
| 모델 실패, 근거 검증 실패 | 새 분석 ID로 새 시도(배치) | 유지. 실패한 시도의 툴 기록은 새 시도의 근거로 쓸 수 없어(`PublicationStore._evidence`) 모델 응답을 시도 사이에 재사용하지 않는다 |
| 실행 제어 Lambda 스로틀 | 자리 확보 재시도 3회를 다 쓰면 배치가 시도 하나를 잃는다 | 아래 '실행 제어 Lambda 스로틀' |
| 입력 오류(ALPHA-1162) | 두 시도 모두 모델 호출 전에 거부된다(약 1분) | 지금은 둔다. 워커가 원인 문구를 지워 배치가 구분하지 못한다 |
| 저장 뒤 관측 업로드·응답 유실 | 전망은 DB 상태로 판정(배치, API) | 유지. 가격변동은 F4처럼 전달이 빠질 수 있어 B의 재시도가 이를 줄인다 |
| 가격변동 분석 실패 | **재시도 구현이 없다.** 분석 ID가 사건에서 나오고 실행 이름은 90일 동안 다시 쓸 수 없다 | 시도 번호를 넣은 새 ID로 다시 시도하는 것은 가능하다. 그러려면 요청 저장소의 `source_event_id` 유일 키(사건당 요청 1개), ID 규칙, 회수 조회(`is_retracted`가 요청 행으로 사건 좌표를 찾는다)를 함께 바꿔야 한다. 허용 지연을 정한 뒤 결정한다 |
| 08:00 마감 | 마감 뒤 새 시도를 시작하지 않는다 | 유지 |

같은 분석 ID는 한 번만 돈다(실행 이름, manifest). 실패 뒤 새 시도는 모델을 다시 부른다. 같은 작업의 두 시도가 모두 완료되는 경우는 남는다. 배치가 단건을 1,500초 넘게 기다리다 다음 시도로 넘어갔는데 옛 단건이 끝까지 돈 경우다. 그러면 발행이 둘이 되고 최신 조회는 나중 것을 쓴다. 정확히 한 번은 보장하지 않는다.

### 확인하지 못한 것

- 워커(1 vCPU)의 연결 1회 비용과 그 구간별 내역. Lambda 두 개의 소요는 상한 참고값이다.
- RunTask 도중 실행이 중단될 때 태스크가 실제로 남는지, 얼마나 자주인지(C2의 틈이 실제로 열리는지).
- ECS가 멈춘 태스크를 보여 주는 시간의 정확한 경계(C1이 시작되는 시점).
- 동시 수를 3보다 올릴 때의 SFN `DescribeExecution`·`GetExecutionHistory` 호출량과 API 한도, DeepSeek 동시 호출(이번 검토의 전제), RDS `db.t4g.small`의 CPU 크레딧.
- 실제 RDS 재시작과 장애 조치. 로컬에서는 세션 종료와 로그인 차단으로 흉내 냈다.

### 구현 전에 해결할 것과 미룰 것

B 구현 전에 해결할 것:

1. 자리 회수의 `MISSING` 결함(C1). 지금 배포에도 해당한다. 끝난 실행의 태스크가 `MISSING`이면 멈춘 지 오래된 것으로 보고 회수하고, 판정할 수 없는 자리 하나 때문에 다른 ETF의 자리 확보까지 실패하지 않게 그 자리만 점유로 둔다. 실행 제어는 팀원 담당(ALPHA-1161)이라 범위 조율이 먼저다. (검토 당시 권고다. 최종 구현은 `MISSING`을 회수 근거로 쓰지 않는다 — 아래 '구현 결과' C1.)
2. 회수 불확실성 보완(C2). 워커에 단건 실행 ARN을 넘기고, 발행 저장과 가격변동 전달 등록 트랜잭션에서 자기 자리 행을 `FOR SHARE`로 확인한다(최종 구현은 발행 저장에서만 확인한다 — 아래 '구현 결과'). 행이 없으면(회수됨) 발행하지 않는다. 행이 있으면 회수의 `DELETE`가 그 트랜잭션 뒤로 밀려, 다음 실행은 이 발행을 이전 설명으로 본다. 새 표, heartbeat, 시간 만료는 없다. 대안은 워커의 ETF 락만 연결 하나로 계속 쥐는 것(분석당 writer 1개 상시)이다.
3. 위 '재시도'의 범위(연결 계열 오류만, 트랜잭션 단위, 시간 상한)와 `save_run` 되읽기.
4. 비밀값·클라이언트 캐시, 정의 등록과 관측 내보내기 묶기, 연결 시간 로그.

미룰 것: 동시 수 상향, 작은 풀·프록시(연결 시간 측정 뒤), 가격변동 재시도(허용 지연 결정 뒤), 늦은 사건의 처리 정책, 입력 오류 분류.

**실행 제어 Lambda 스로틀**(팀원 담당, 범위와 검증 조건만): 예약 동시 실행을 1보다 올리고(정합성은 C5) writer 역할 한도 산식에 그 수를 넣는다. 자리 확보·반납 `Retry`에 `Lambda.TooManyRequestsException` 전용 규칙을 두고 지터와 최대 대기를 준다. 호출 1회가 1초 이상인 원인(비밀값·클라이언트를 매 호출 생성, 256 MB)을 줄인다. 검증은 계약 테스트(`modules/analysis-v2/tests/test_single_analysis.py`)에 재시도 규칙을 넣고, dev에서 단건 6건 이상을 동시에 시작해 자리 확보가 재시도를 다 쓰지 않는지 본다.

검토 권고와 달라진 점은 셋이다.

- C1: 회수 근거는 실행 이력의 태스크 `STOPPED`, ECS의 `STOPPED` 응답, RunTask를 부르지 않은 실행뿐이다. `MISSING`, 빈 응답, 시간 경과, 조회 실패는 근거가 아니다. 판정하지 못한 자리는 점유로 남아 상한과 같은 종류·ETF 제약에 들어가고, 다른 자리 판정은 계속한다. 수동 복구는 ECS `STOPPED`를 확인한 자리만 지운다(`src/apps/cloud/analysis-engine-v2/docs/price-automation.md`). #1111 초안은 제출 10분 뒤 `MISSING`을 근거로 썼지만, `MISSING`은 태스크가 멈췄다는 기록이 아니어서 머지 전에 뺐다(AWS 문서의 '최대 5분 대기'는 재시도 권고이지 완전성 보장이 아니다).
- C2: RunTask를 불렀지만 태스크 ARN이 기록되지 않은 실행의 자리는 회수하지 않는다(`task-unrecorded`). #1111 초안의 '10분 뒤 ECS 목록에 같은 종류·ETF의 멈추지 않은 태스크가 없으면 회수'도 같은 이유로 뺐다. RunTask를 부르기 전에 끝난 실행의 자리는 곧바로 회수한다. B의 발행 시 자리 확인은 회수 판정이 틀렸을 때 옛 워커가 결과를 내지 못하게 하는 두 번째 방어다.
- 소유권 확인은 발행 저장에서만 한다. 전달 등록은 이미 커밋된 발행을 원장에 옮길 뿐이고, 여기서 막으면 발행은 있는데 전달이 빠지는 경우가 생긴다. 늦은 결과가 더 새 전달을 덮지 않는 것은 기존 `enqueue_movement` 비교가 맡는다.
